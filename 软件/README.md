# Studio Shell —— 小软件的仿真外壳（项目清单驱动的算法装配）

> 一句话：**把控制算法从主程序里拆出来，变成"新建一个文件 + 在列表里加一个名字"。**
> 底座是官方的 MuJoCo Studio（物理引擎 + 界面 + 插件机制），上面这一层是我们自己的。

## 1. 怎么跑（★ 必须用 `.venv` 的 python）

```bash
cd "$HOME/Desktop/驭臂"

.venv/bin/python 软件/主程序.py            # 开窗口（默认加载：关节 PD 控制）
```

> 缺界面层和插件系统。用错环境时主程序会直接打印中文提示告诉你怎么改，不会莫名其妙地崩。

## 1.5 这个界面为什么和教程里的 `mujoco.viewer` 长得不一样？

**因为是两套完全不同的界面程序**，不是同一个界面换了皮肤：

| | 教程 10/11 号脚本（第 1 步） | 本外壳（第 2 步） |
|---|---|---|
| 界面程序 | `mujoco.viewer`（`viewer.py`） | MuJoCo **Studio**（`native_viewer.py`） |
| 渲染器 | 经典 OpenGL | **Filament PBR**（金属反光、材质质感） |
| 界面风格 | 简单工具栏 + 几个滑杆 | **可停靠的多面板工作台**（官方 19 个面板） |
| 默认主题 | ImGui 默认**深色** | 官方默认**浅色（白底）** |
| 定位 | 快速看模型的"仪表盘" | 完整的仿真工作台 |

所以"白底 + 边框"是**正常的** —— 那是 Studio 的浅色主题。

### 换成深色（和以前一样）

```bash
.venv/bin/python 软件/主程序.py --主题 dark     # 深色 ← 本外壳默认值
.venv/bin/python 软件/主程序.py --主题 light    # 浅色（官方默认）
.venv/bin/python 软件/主程序.py --主题 classic  # 经典
```

也可以在窗口里改：顶部菜单 **Appearance → base theme**。主题会存进 `~/.mujoco.ini`
（`[Studio][UX] theme=0/1/2`），下次启动自动沿用。

> 本外壳**默认就是深色**（和老 viewer 观感一致）；想要白底就用 `--主题 light`。

### 界面语言（中文 / English）

```bash
.venv/bin/python 软件/主程序.py                 # 默认中文
.venv/bin/python 软件/主程序.py --语言 en        # English
```

窗口里也能切，**两处都能一键切**：

| 位置 | 怎么用 |
|---|---|
| **顶部那一行**（File / Help 那一排） | 一个语言按钮：中文模式显示 `EN`，英文模式显示 `中文`，**点一下即切** |
| **Appearance 菜单** | `语言 ▸ 中文 / English`（当前那项打勾） |

选择会存进 `输出/设置.json`（`语言` 键），下次启动沿用；优先级是
**命令行 `--语言` > 环境变量 `YUBI_LANG` > 存档 > 默认中文**。

**能中文到哪一层（重要）**：

| 层 | 能不能切 |
|---|---|
| 我们自己的 8 个面板 + 面板窗 + 我们挂的菜单 | ✅ 全中文 |
| 官方**用 Python 画**的顶栏（`File / Simulation / View / Help` 及其条目） | ✅ 能（做法：包装 `imgui.BeginMenu/MenuItem` 查词表翻译，不改官方文件） |
| 官方**用 C++ 画**的面板（`Options` 里 19 个段、`Inspector` 里的 `Noise/Joints/…`） | ❌ **永远英文** —— 字符串编译在 `ux.*.so` 里 |

**翻译的规矩（有自检兜着）**：界面上任何一句话都必须走 `软件/文案.py` 的
`文案.取("键")`；`验证/语言自检.py` 用 AST 检查"真正画给 imgui 的字符串"，
发现写死的界面文字就报错 —— 这样切到英文时不会漏出中文（反之亦然）。

★ 中文字形靠 `工具/打补丁_中文字体.py` 补进官方字体。`.venv` 是"可重建、不进 git"的，
**重建环境后要记得重打补丁**；没打补丁时程序会**自动回退英文**并在终端提示，
不会甩给你一屏 `?????`（判定：`工具/打补丁_中文字体.py --状态`）。

### 窗口里有什么

| 位置 | 内容 |
|---|---|
| 3D 视图 | 机械臂；左键拖动转视角、右键平移、滚轮缩放、Ctrl+拖动可以"抓住"机械臂拉 |

终端里每 2 秒会打印一行插件状态，例如：

```

```

看到"步数"在涨、"当前误差"收敛到 0，就说明**算法真的在控制机器人**，不是只有窗口在画。

## 1.6 版本管理（git）

本项目已纳入 git（2026-09-23 起），基线 tag 是 `v0.5.2-基线`。日常三条命令：

```bash
git status              # 改之前先看干不干净
git diff                # 看"到底改了什么"（比任何说明都可靠）
git checkout -- <文件>   # 改坏了回退
```

**为什么有些东西不在 git 里**（理由逐条写在根目录 `.gitignore`，判断标准是"能重建的不进库"）：

| 不进库 | 重建方式 |
|---|---|
| `.venv/`、`离线依赖/` | `bash 工具/重建环境.sh` |
| `小软件.app`、`图标.icns` | `工具/生成图标.py` → `工具/打包应用.py --名字 小软件 --标识 local.digitwin.yubi` |
| `启动日志.txt`、`输出/*.json`、`输出/04_记录/` | 运行产物 |

★ **改 `.app` 行为时的注意点**：`启动.sh` 是**生成物**，由 `工具/打包应用.py` 里的
`启动器模板` 生成。要改启动逻辑就改**那个模板**，改完重新打包；
直接改 `小软件.app/Contents/Resources/启动.sh` 的话，下次打包就被覆盖
（而且这个文件不在 git 里，改动也不会被记录）。

## 2.5 默认行为：点开模型是静止的，算法要手动 Apply

| | 现在 |
|---|---|
| 点开/切换模型 | **不加载任何控制算法**（5 个项目的 `算法` 字段都是 `[]`），**物理冻结**在默认位置 |
| 左上角【Display】 | `Load gravity` —— 勾上才施用重力（物理推进）；取消则回默认位置并冻结 |
| 开始运动控制 | 必须在【Algorithms】面板勾选算法 + `Apply`；**光挂算法不动，还要勾重力** |

**机制在哪**（改这块代码前必读）：

| 事 | 在哪 | 为什么 |
|---|---|---|
| 冻结/解冻 | `重力桥.重力应用器` + `插件系统.安全注册表.加冻结判据()` | 冻结靠"注册表不派发 `StepEvent`"，**不是**改暂停快照 —— 官方 ViewerApp 实测不发快照，靠它必失效（**契约例外 ③**） |
| 它是内置件而非算法 | `启动.py` 里 `注册表.加插件(重力应用器)` | 需求是"所有模型都静止"，不能取决于"恰好装了某个算法"；否则清空算法列表就会**静默失效** |
| 换模型才重置重力 | `重力桥.重力应用器.收到模型()` 比对模型路径 | 换**算法**也会走这条通知，那时重置重力会让用户莫名其妙（"勾了重力，一点 Apply 又没了"） |
| 内置件也要收到模型 | `启动.py` 的 `通知模型加载(list(注册表._目标), …)` | 原来只通知新装配的用户算法 → 内置件永远拿不到模型 → 不复位不冻结 |

## 3. 加一个控制算法（三步，**零改动**）

```bash
# ① 复制模板
cp 算法库/通用/我的控制律_模板.py 算法库/通用/我的算法.py

# ② 写算法：打开 我的算法.py，改类名/名称/英文名/说明，然后在 每步控制() 里写你的东西

# ③ 什么都不用改 —— 项目文件里 算法 写 "*" 时，新算法**自动就会被加载**
#    想只挂到某几个项目上，就在那些项目文件的 算法 列表里写上 {"插件": "我的算法"}
```

### 在界面上换算法（【Algorithms】面板）

选完机械臂之后要改算法，不用碰文件：面板窗里的【算法】段 →
勾选 / 用 `^` `v` 调序 → `Apply (temporary)` 立即生效，或 `Save to project file` 写回项目文件。

实现要点（改这块代码时先看这三条）：

| 事 | 在哪 | 为什么这么安排 |
|---|---|---|
| 界面只"说想要哪几个"，装配由仿真线程做 | `模型桥.应用算法命令` → `模型桥.算法选择器` → `启动.py` 的 `换算法()` 回调 | 装配要换掉**正在被仿真的插件实例**，界面线程不能碰（跨线程改状态） |
| 覆盖项目文件的算法列表 | `装配器.按项目装配(..., 算法覆盖=[...])` | 传了就忽略项目文件的 `算法` 字段，其余字段（参数/外观）照旧 |
| Apply 与 Save 分开 | `算法覆盖` 与 `落盘` 是两个独立参数 | 试错不该弄坏项目里存好的预设；`落盘=True` 才写回文件 |
| 界面怎么知道有哪些可选 | `项目状态.算法库`（状态消息新增字段） | 仿真侧启动时扫一次算法库带上；界面不自己扫盘 |
| 面板上的勾选用什么当键 | **插件名**（`关节pd控制`），显示时才翻成 `英文名` | 状态消息给的是显示名、项目文件给的是插件名 —— 不用插件名做键就会串 |

### 算法与模型是怎么绑上的（本节是方案 C 的核心）

以前"用哪些算法"写死在 `主程序.py` 的【插件清单】里（一份硬编码的 Python 列表），换个模型还是同一套算法。
现在改由 `项目/*.json` 声明：

```json
{ "项目": "UR5e_基础PD",
  "模型": "模型/universal_robots_ur5e/ur5e_torque.xml",
  "算法": "*",
  "参数": { "关节 PD 位置控制": { "KP": 320.0 } } }
```

**点一个模型时的完整流程**（实现分散在三个文件里，这里给出对应位置）：

| 步 | 做什么 | 在哪 |
|---|---|---|
| ① | 界面发 `换模型命令` | `面板/模型库面板.py` → `模型桥.py` |
| ② | 外壳加载模型、重绑 `model/data` | `启动.py` 的 `切换模型()` |
| ③ | 按 `模型` 字段反查项目 | `项目.py` 的 `按模型找项目()` |
| ④ | 读项目文件、解析 `算法` 字段 | `项目.py` 的 `读项目()` / `解析算法()` |
| ⑤ | 逐文件 import 并实例化（按路径生成唯一模块名，同名文件不互相覆盖） | `装配器.py` 的 `导入算法文件()` / `找插件类()` |
| ⑥ | **兼容性预检**：不兼容的不启用，把原因写进报告 | `装配器.py` 的 `检查兼容性()` |
| ⑦ | 整组替换用户算法（内部插件保持常驻） | `插件系统.py` 的 `安全注册表.设用户插件()` |
| ⑧ | 参数应用器**重绑**（不重绑滑杆会静默失效），回填项目里存的参数 | `参数桥.py` 的 `重绑()`；`启动.py` 的 `_恢复参数()` |
| ⑨ | 通知各算法（`收到模型` / `绑定模型路径` / `模型已切换`） | `插件系统.py` 的 `通知模型加载()` |
| ⑩ | **立刻**发一条项目状态给界面 → 算法列表马上更新 | `模型桥.py` 的 `项目状态发布器` |

一个插件的完整长相（其余都是注释）：

```python
import 插件系统 as 插件
from 插件系统 import 控制插件, 每步

class 我的插件(控制插件):
    名称 = "我的控制算法"          # 会显示在启动清单里
    版本 = "0.1"
    说明 = "一句话说清它干什么"

    @每步                                  # ★ 贴标签 = 参与每一步仿真
    def 每步控制(self, event: 插件.messages.StepEvent) -> bool:
        数据 = event.data
        数据.ctrl[:] = 数据.qfrc_bias       # ← 你的算法（这里只是重力补偿）
        return False                        # False=不拦截（推荐）
```

**硬性要求**：

1. `@每步` 的方法**必须有类型标注**：`event: 插件.messages.StepEvent`（官方定的，不写会报错）；
2. 文件名**不能以数字开头**（Python 的 import 规则）——顺序由项目文件里的算法列表顺序决定；
3. `每步控制()` 里要写的是 `event.data.ctrl[:]`（6 个关节的力矩，N·m）；
4. **面板上只能画 ASCII**（官方 UI 字体没有中文字形）。`名称`/`说明` 可以用中文（只出现在终端），
   面板上显示的名字写 `英文名 = "..."`；`指标()` 的曲线名用中文前先在 `界面文字.py` 登记。

**可选的两个钩子**（换模型时会用到，写算法时值得知道）：

| 钩子 | 什么时候被调 | 用来干什么 |
|---|---|---|
| `模型兼容性(self, 模型) -> str` | 装配时、**换模型之前** | 返回 `""` = 兼容；返回原因串 = **不启用它**并把原因显示给用户。好过跑起来抛异常被"出错隔离"永久停用 |
| `模型已切换(self, 路径, 模型, 数据)` | 换模型**之后** | 清掉跟旧模型绑定的缓存（采样数据、索引、上次结果）。标准范例见 `算法库/通用/参数辨识插件.py` |

## 4. 我们给官方补的两个能力（官方没有）

### ① 插件出错隔离

官方 `plugin_registry.dispatch` 里**没有 try/except**：任何一个插件抛异常，整条分发链断掉，软件直接挂。
实测复现：

```python
PluginRegistry([坏插件()]).dispatch(ResetEvent())
# → RuntimeError: 我是坏插件   ← 直接冲出到调用方
```

我们的做法（`插件系统.安全注册表`）：**逐个插件单独调用**，谁崩了只影响谁：

```
⚠ 插件【故意会崩的插件】出错（已隔离，软件继续运行）：IndexError: list index out of range
  出错位置：_临时坏插件.py 第 7 行（每步控制）
  → 先跳过它继续跑；再错一次就停用它。改好代码后重启即可。
✗ 插件【故意会崩的插件】再次出错 → 已停用。其他插件和界面不受影响。
```

实测结果：坏插件被停用后，**好插件照常跑了 1500 步、机器人仍被控制到 0.0000° 误差**。

## 5. 两个必须知道的"坑"（都踩过并解决）

### 坑 1：macOS 上 `launch_passive` 开不了窗

官方推荐的写法在 macOS 上直接报错：

```
ERROR: Error creating window: NSWindow should only be instantiated on the main thread!
```

原因：官方把创建窗口的活儿丢给 daemon 线程，而 macOS 要求窗口只能在主线程建。
**我们的排法**（`启动.py`）：主线程跑窗口、后台线程跑仿真，中间用官方现成的消息通道通信。
这是"二次开发"里唯一一处必须偏离官方写法的地方，已经封装好，你不用管。

### 坑 2：真正推进物理的是 `StepControl` 插件，不是 `sync`

`ViewerHandle.sync` 只负责**派发** `StepEvent`；官方 `StepControl` 插件收到 `StepEvent` 才去 `mj_step`。
所以我们做"逐个插件隔离"时**必须把 StepControl 一起注册进来**，否则会出现：

> 控制律被调用了 25 万次，但仿真时间一直停在 0，机械臂纹丝不动。

`插件系统.安全注册表` 里已经把它排在第一位（它优先级 INTERNAL，本来就最先执行），
同时它负责的**暂停 / 单步 / 倍速 / 噪声 / 发散自动重置**也就都能用了。
