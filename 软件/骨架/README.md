# 骨架 —— 我们自己的边界层

> **它是什么**：一份"边界合同" + 两个看门工具。
> 外壳能用官方的哪些东西，全在 `官方接口清单.py` 里登记；清单之外偷偷用了官方内部 API，就是越界。
>
> **一句话**：官方把插件系统标为"实验性"，而这个模块**我们永远无法完全摆脱**
> （16 个 C++ 扩展拷不走）。所以不做"搬代码"这种无效防御，
> 而是**把边界写下来、盯住它**——官方一改，启动第一秒就告诉你断在哪、该改哪一行。

---

## 1. 这个目录里有什么

| 文件 | 作用 |
|---|---|
| `官方接口清单.py` | ★ 21 项官方依赖的**可执行检查表**。每项含：编号、说明、怎么取值、怎么验证、断了改哪个文件 |
| （本文件） | 说明为什么这样设计、怎么用、官方升级时怎么办 |

配套的两个"锁"在外面：

| 文件 | 作用 |
|---|---|
| `requirements.lock`（包根） | 把**实测跑通过**的版本钉死（`mujoco==3.13.0` 等） |
| `工具/检查版本锁.py` | 随时核对当前环境是否与锁一致 |

**两道防线合起来才完整**：
- 版本对了，接口不一定对（官方可能发了同版本号的修订）→ 要靠 `官方接口清单`
- 接口对了，版本也未必对（比如换了 glfw）→ 要靠 `requirements.lock`

## 2. 怎么用

### 日常（什么都不用做）

启动外壳时会**自动跑一次**，只列出错项，不刷屏：

```
【环境自检】
  mujoco 版本 : 3.13.0   （实测跑通过的版本：3.13.0）
  ...
  ✓ 官方接口自检：21 项全部正常（窗口/渲染/面板/消息机制都还在）
```

### 排查时（逐条看）

```bash
cd "$HOME/Desktop/驭臂"
.venv/bin/python 软件/主程序.py --自检      # 逐条列出 21 项
.venv/bin/python 软件/骨架/官方接口清单.py   # 直接跑这个模块也行
.venv/bin/python 工具/检查版本锁.py                 # 核对版本
```

### 在外壳代码里取用官方接口

```python
from 骨架 import 官方接口清单 as 官方
ViewerApp = 官方.取("viewer_app.ViewerApp")      # 按编号取，第一次用到才 import
```

**约定**：外壳代码要新用一项官方接口时，**先在 `清单` 里加一条**，再用它。
这样它才会被看住；否则就是在"清单之外偷用官方内部 API"。

## 4. 官方升级了怎么办

### 第一步：让自检告诉你

```bash
.venv/bin/python 软件/主程序.py --自检
```

失败项会直接打印"该改我们哪个文件"和"受影响的地方"，例如：

```
✗ messages.handler    取不到（AttributeError: module '...messages' has no attribute 'handler'）
    → 该改我们这边：插件系统.py → 每步 = messages.handler；若参数名变了，改这一行
    → 受影响：算法库/通用/*
```

### 第二步：两条路选一条

| 情况 | 做法 |
|---|---|
| **只是想赶紧能用**（推荐先做这个） | 退回实测版本：`.venv/bin/pip install -r requirements.lock` |
| 确实需要新版本 | 按自检给的指引改外壳（通常只改 `插件系统.py` 或 `启动.py` 的一两行），改完跑一遍验收：`--自检` 21 项全绿 + 开窗 + 控制律收敛 |

### 第三步：改完要更新台账

```bash
# 1) 更新版本锁（改 requirements.lock 里的版本号）
# 2) 刷新"零改动自检"的基准（否则它会把你的正当修改报成"越界"）
.venv/bin/python 软件/零改动自检.py --建立
# 3) 若清单本身也要加条目，同步更新 官方接口清单.py
```

## 5. 一个真实的例子（这套机制怎么救场）

实测：把 `messages.handler` 临时删掉（模拟官方改名），自检立刻报出：

```
改坏 messages.handler 后：13 正常 / 8 失败
→ 自检定位到: messages.handler
→ 说明: 取不到（AttributeError: module '...messages' has no attribute 'handler'）
→ 该改: 插件系统.py → 每步 = messages.handler；若参数名变了，改这一行
```

**没有这套机制会怎样**：外壳能启动、窗口能开，
但你的控制律**一声不响地不再被调用**（因为 `@每步` 贴标签失败），
你可能要花半天才能定位到"原来是官方把装饰器改名了"。

## 6. 为什么不"把官方代码搬过来"（背景，避免以后重复讨论）

| 实测事实 | 结论 |
|---|---|
| 最小闭包 **12 个文件 2584 行**（其中 GUI 层 1494 行，改动最频繁） | 搬过来工作量不小，且要跟着官方改 |
| **16 个 C++ 扩展永远拷不走**（窗口/渲染/界面/物理） | 搬完 Python 层，**风险最大的部分一点没减少** |
| 版本锁定靠 `mujoco==3.13.0` 一行就够 | 搬代码不是"锁定版本"的必要手段 |

所以第 3 步的做法是：**钉住边界 + 能扩展**，而不是搬代码。
完整论证见 `第3步_建自己的骨架_规划报告.md`。
