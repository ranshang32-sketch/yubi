## 一、先给结论：双方各强在哪

### 驭臂强于 Ultralytics 的地方（不要改掉）

|---|---|---|---|

| 2 | **可机检的外部依赖边界合同**（21 项） | `软件/骨架/官方接口清单.py`（422 行） | Ultralytics 只有 `AGENTS.md` 里的散文式扩展说明，**没有可执行的边界自检** |

| # | 差距 | 具体表现 |

## 二、驭臂的插件系统解剖：**三个**子系统，不是一个

这是理解驭臂架构的第一件事：`软件/插件系统.py` 并不是驭臂插件机制的全部，
项目里实际上并存着**三套彼此独立的"插件系统"**，各有各的注册方式、生命周期与扩展点。

| | 子系统 A：官方 Studio 插件 | 子系统 B：驭臂兼容层 | 子系统 C：自研面板 |
|---|---|---|---|
| **入口文件** | `mujoco/experimental/studio/plugin_registry.py`（官方，62 行） | `软件/插件系统.py`（366 行） | `软件/启动.py:269-303` + `面板/面板注册表.py` |
| **发现方式** | `_discover_handlers()` 扫 `dir(type(plugin))` 找 `_HANDLER_INFO_ATTR` | 包住 A，改成**逐个插件单独调用** | **目录扫描**：`面板/*.py` 里有 `面板类` 就是面板 |
| **激活方式** | 构造 `PluginRegistry([...])` 传入实例 | `软件/主程序.py:39-67` 硬编码 import + 列表 | **放文件即生效**（打开验证：新建一个含 `面板类` 的 .py 即被发现） |
| **路由** | 按消息类型建 dict，`__mro__` 匹配，按 `priority` 排序 | **每条消息重建 handler 表**（每次 `_discover_handlers`） | `@messages.handler` + `面板注册表.每帧(self)` |
| **出错隔离** | ❌ 无（`dispatch` 里没 try） | ✅ 逐个隔离 + 第二次出错停用 | ✅ 每个面板单独 try（`启动.py:293`） |
| **规模** | — | 4 注册表/应用器 + 5 桥 | 10 个面板 + 2 个工具模块（2550 行） |

### 2.1 一个关键观察：项目里最好的插件机制在**面板层**，不在算法层

`软件/启动.py:269-303` 的面板加载逻辑是纯目录扫描：

```python
for 文件名 in sorted(os.listdir(面板目录)):
    if not 文件名.endswith(".py") or 文件名.startswith("_") or 文件名 == "曲线基类.py":
        continue
    模块 = __import__(模块名)
    面板类 = getattr(模块, "面板类", None)      # ← 唯一的契约：模块里有"面板类"
    if 面板类 is None:
        continue                               # 不是面板文件（比如纯工具模块）
```

**本机验证**（用临时目录复刻这段逻辑，未修改项目任何文件）：往目录里丢一个
`面板/探针面板.py`（4 行，只有 `面板显示名` 和 `面板类`），自动发现输出 `['探针']`。

也就是说：**面板做到了"放文件即生效"，控制算法还停留在"改主程序列表"**。
这两个子系统长在同一个 `启动.py` 里，标准却不一致——这是最容易补齐、收益最直接的一处。

### 2.2 官方那一层已经被正确隔离（这部分设计很好）

`软件/插件系统.py:30-60` 把所有官方 import 收在一个函数里，失败时抛中文提示：

```python
def _导入官方():
    try:
        ...
        from mujoco.experimental.studio import messages, step_control, viewer_app, ...
    except ImportError as e:
        提示 = (f"\n✗ 当前 Python 环境里没有可用的 Studio 插件系统：{e}\n"
                f"  原因：Studio 插件系统只在官方 pip 包（mujoco >= 3.12 的完整版）里有，\n"
                f"        conda 渠道装的 mujoco 是「零件版」，不含界面层和插件系统。\n")
        raise SystemExit(提示) from e
```

这是整个项目最值得保留的设计之一：**唯一的官方 API 入口 + 人话版失败信息**。
配合 `骨架/官方接口清单.py` 的 21 项可执行检查，形成了"版本锁 + 接口锁"两道防线。

## 三、写一个控制算法，实际要面对的全套契约

这是本报告的核心事实。驭臂的插件契约**不是一份文件**，而是散落在五个地方，
其中**两个连官方接口清单里都没有登记**（下表"登记状态"列）。

### 3.1 钩子全表（按"谁调用"分组，含证据与文档覆盖）

| # | 钩子 | 谁调用 | 调用时机 | 定义位置 | 文档覆盖 | 登记状态 |
|---|---|---|---|---|---|---|
| 1 | `名称/版本/说明/作者` | 外壳打印清单 | 启动 | `插件系统.py:84-87` | ✅ | ✅ |
| 2 | `每步控制(self, event)` + `@每步` | 官方 `dispatch`（经安全注册表） | **每步（500 Hz）** | `插件系统.py:62-81` | ✅ 模板里 | ✅ 清单第 2 项 |
| 3 | `插件状态() -> dict` | 外壳终端每 2 秒 | 2 Hz | `插件系统.py:90-92` | ✅ | ✅ |
| 4 | `可调参数() -> dict` | `参数桥.采集可调参数` | 10 Hz | `插件系统.py:108-110` | ✅ | ❌ **清单里没有** |
| 5 | `设置参数(名, 值) -> str` | `参数桥.参数应用器.收参数` | 拖动时 | `插件系统.py:112-120` | ✅ | ❌ **清单里没有** |

| 7 | `绑定模型路径(路径)` | `启动.py:129-131`（`hasattr` 鸭子探测） | 模型切换 | **只在插件里**（`参数辨识插件.py:140`） | ⚠️ 3 处 | ❌ **无定义、无登记** |
| 8 | `模型已切换(路径, 模型, 数据)` | `启动.py:132-136`（同上） | 模型切换 | **只在插件里** | ❌ **0 处文档** | ❌ **无定义、无登记** |

| 10 | `状态消息()` | `辨识桥.发布器` | 5 Hz | `模型桥.py:233`（另一个类上） | ✅ | ❌ **清单里没有** |

### 3.2 这张表的三个问题

**问题 1：契约的"真相源"是五个文件的注释，不是一个文件。**
第 7、8 号钩子只在 `启动.py` 的 `hasattr` 探测里存在：

```python
# 软件/启动.py:129-136
for _p in 插件列表:
    if hasattr(_p, "绑定模型路径"):
        _p.绑定模型路径(路径)
    if hasattr(_p, "模型已切换"):        # 可选钩子：清掉跟旧模型绑定的缓存
        try:
            _p.模型已切换(路径, 模型, 数据)
        except Exception as _异常:
            print(f"⚠ 插件【{getattr(_p, '名称', _p)}】的 模型已切换() 出错：{_异常}")
```

注意这段代码的**不一致**：`绑定模型路径()` 没有 try/except，`模型已切换()` 有。
也就是说第 7 号钩子里抛异常会**冲出仿真循环**（`启动.py:241` 的兜底会打印"仿真线程出错"并**整个仿真线程退出**）。
`参数辨识插件.py:140-143` 里 `绑定模型路径()` 的实现确实是可能抛异常的（要重建模型）。

**本机验证**：
```
$ grep -rn "模型已切换" --include="*.py" .        → 只有 启动.py（调用方）+ 参数辨识插件.py（实现方）
$ grep -rn "模型已切换" --include="*.md" .        → 0 处
```

**问题 2：三个子系统对"同一件事"用了三套写法。**
`每步` 是装饰器路由、`可调参数` 是鸭子类型拉取、`模型已切换` 是 `hasattr` 推送。
写算法的学生必须记住"哪个钩子用哪种方式声明"，而这件事**没有一处写全**。

**问题 3：官方接口清单登记了"官方的形状"，没登记"我们的形状"。**
`骨架/官方接口清单.py` 的思路（编号 + 说明 + 怎么验证 + 断了改哪个文件）**极其好用**，
但它只覆盖对官方的 21 项依赖。驭臂**自己对插件的 10 个钩子**——同样是跨文件、同样会随重构改名——
反而没有这样一张表。第 4、5、9、10 号钩子改个名字，受影响的是 `参数桥.py`、`指标桥.py`、`辨识桥.py` 三个文件，
而**没有任何自检会告诉你**。

### 3.3 一个隐藏的性能事实（实测数据）

`安全注册表._单独派发` 每条消息都重建 handler 表：

```python
# 软件/插件系统.py:219-229
def _单独派发(self, 插件, 消息) -> None:
    from mujoco.experimental.studio import plugin_registry
    for info, 方法 in plugin_registry._discover_handlers(插件):  # noqa: SLF001
        if not issubclass(type(消息), info.message_type):
            continue
        try:
            方法(消息)
        except Exception as 异常:
            self._处理异常(异常, 消息, 插件)
```

**本机实测**（`.venv` 环境，Python 3.10.21）：

| 操作 | 单次耗时 |
|---|---|
| 官方 `_discover_handlers(plugin)` | **2.93 µs** |
| 官方 `PluginRegistry.dispatch(msg)`（表已建好） | **0.298 µs** |
| 驭臂重建 6 个插件的 handler 表 | **≈ 17.6 µs / 次** |

主循环每轮派发 1 条 `StepEvent` + 若干 viewer 事件/快照，即**每轮多花约 20 µs 纯做反射**，
是官方设计（构造时建表一次）的 **≈ 60 倍**。以 500 Hz 计约占 1% CPU——**不致命，但完全没必要**。

官方 `PluginRegistry.__init__` 明明就是在构造时建表（`plugin_registry.py:39-45`），
驭臂之所以改成每轮扫描，是为了支持 `加插件()` 运行期挂载。
代价本可以避免：**建表一次 + `加插件()` 时增量更新**即可。

## 四、插件 ↔ 模型：绑定契约的薄弱点（有真实事故）

### 4.1 现状：模型侧有清单，算法侧什么都没有

`模型/模型库.json` 是模型侧的唯一清单，每个条目声明了：`标识 / 显示名 / 类别 / 目录 / 扭矩模型 / 可控制 / 自由度 / 执行器数 / 许可 / 模型文件`。

**本机实测各扭矩模型的真实维度**：

| 模型 | nq | nv | nu | `关节PD控制插件` 能否工作 |
|---|---|---|---|---|
| `universal_robots_ur5e/ur5e_torque.xml` | 6 | 6 | 6 | ✅（按 6 维绑定） |
| `universal_robots_ur10e/ur10e_torque.xml` | 6 | 6 | 6 | ✅ |
| `franka_emika_panda/panda_torque.xml` | 7 | 7 | 7 | ⚠️ 取决于启动时先加载了谁 |
| `kuka_iiwa_14/iiwa14_torque.xml` | 7 | 7 | 7 | ⚠️ 同上 |
| `ufactory_xarm7/xarm7_torque.xml` | 7 | 7 | 7 | ⚠️ 同上 |

**注意最后一列**：算法能不能用，**不取决于算法，而取决于启动顺序**。
`关节PD控制插件` 在第一次 `每步控制()` 时把 `home` 姿势缓存在 `self.目标`（`关节pd控制.py:76-84`），
这份缓存**绑定了当时的关节数，之后永不更新**。

### 4.2 真实事故复盘（证据：`启动日志.txt:1083-1086`）

```
【模型】✓ 已切换到 Universal Robots UR10e（6 轴、耗时 214 ms）
⚠ 插件【关节 PD 位置控制】出错（已隔离，软件继续运行）：ValueError: operands could not be broadcast together with shapes (7,) (6,)
  出错位置：关节pd控制.py 第 89 行（每步控制）
  → 先跳过它继续跑；再错一次就停用它。改好代码后重启即可。
✗ 插件【关节 PD 位置控制】再次出错 → 已停用。其他插件和界面不受影响。
  [辨识] 模型已切换为 ur5e_torque.xml（可辨识 3 个连杆质量）
  [t=  0.27s] 已停用: 关节 PD 位置控制 | 参数辨识(状态=空闲、采样=0、拟合改善=—)
```

事件的真实顺序是：**7 轴模型（Panda/iiwa14）→ 6 轴模型（UR10e）**，
`self.目标` 是 7 维、`数据.qpos` 是 6 维 → 广播失败 → **两次之后插件被永久停用**。

同一份日志里，事故之后用户又切回了 `ur5e`（一个 6 轴、**本可以正常工作**的模型），
但控制器依然保持"已停用"状态——**算法没有坏，是绑定坏了，而系统把账算在了算法头上**。

对应的代码（`算法库/通用/关节pd控制.py:87-91`）：

```python
# 目标优先级：界面滑杆（拖过就听它的）> 本文件里写的目标
目标 = self.目标
if (self.听界面滑杆 and self.界面目标 is not None
        and len(self.界面目标) == len(数据.qpos)):     # ← 只对"滑杆"做了维度检查
    目标 = self.界面目标

误差 = 目标 - 数据.qpos                                # ← 第 89 行：对 self.目标 没有检查
数据.ctrl[:] = self.KP * 误差 - self.KD * 数据.qvel + 数据.qfrc_bias
```

**这个 bug 的结构性含义**：作者**知道**要检查维度（滑杆那行就是证明），
但只在"用户输入"这条路上检查了，漏掉了"模型变化"这条路。
这不是疏忽，是**缺少一个"模型变更"的统一收口点**：
如果插件能实现 `模型已切换()` 来重置缓存（钩子 8 号**已经存在**），
或者系统在切换前做一次兼容性预检，这次事故不会发生。

### 4.3 项目**已经发现过**同一类问题（但只修了现象）

`文档/模型选择与切换_可行性审查.md:135-151` 记录了几乎同构的一次：

> ### 4.2 空场景会把默认控制插件"弄停用"（已实测复现）
> 实测：加载一个只有地面的场景（`nq=nv=nu=0`），派发 3 次 `StepEvent`：
> `✗ 插件【关节 PD 位置控制】再次出错 → 已停用`
> **注意**：出错隔离机制本身工作正常（软件没挂）。但插件被**停用了**，
> 于是用户之后选一个真模型进来，**机械臂不会被控制**（插件已经停用，只能重启）。
> **修法**：给插件加一行保护（`if len(数据.qpos) >= 3:`），或者让外壳在 `nu==0` 时不派发 `StepEvent`。

文档给出的修法是**在插件里加 if**——这修好了"空场景"这一个现象，
但 6 轴 ↔ 7 轴 这个**同类问题换了个马甲又发生了一次**（就是 4.2 节的事故）。

**这是本报告最重要的判断**：项目把"算法与模型的兼容性"当成了**每个插件各自的修养**，
而不是**插件系统的职责**。只要这个定位不变，同类事故会继续以新形式出现。

同一份文档还记录了另一个同源问题（`:153-174`）：

> ### 4.3 参数辨识插件写死了 UR5e 的连杆名
> 实测各模型的连杆名完全不同（ur5e: `forearm_link` / panda: `link0…link7` / iiwa14: `link1…link7` / xarm7: `link_base, link1…`）
> **修法**：给它一张"每个模型辨识哪些连杆"的表（放在 `模型/模型库.json` 里）

**修法早就写出来了，但没有落地**——`模型/模型库.json` 里今天仍然没有"该模型可辨识哪些连杆"的字段。
这是一个**已经设计好、只差 20 行代码**的改进（见第八节 P0-3）。

### 4.4 模型切换链路的现状（两条入口已收口，但实现埋在核心文件里）

好消息：换模型这件事**已经收敛到单一入口**——`软件/模型桥.py` 的 `模型应用器`：

```
界面【模型库】面板 →（换模型命令）→ 模型应用器.收命令 ─┐
官方"拖 .xml 进窗口" →（ModelEvent）→ 模型应用器.收拖拽模型 ─┤
                                                          ↓
                                         启动.py 内嵌的 切换模型() 闭包
                                    （加载 → 重绑 句柄.model/data → 通知窗口 → 通知插件 → 记住模型）
```

坏消息：`切换模型()` 这个约 **50 行的闭包定义在 `启动.py:101-145` 内部**，
而 `启动.py` 是**被哈希钉住的 3 个核心文件之一**（`零改动自检.py`）。
于是"改进模型切换逻辑"和"保持外壳零改动"这两个目标直接冲突。
项目已经为此开过一次契约例外（`插件系统.py:131-144` 的 `_当前注册表`/`取注册表()`），
并留了话："**这是目前唯一的例外**"。**第二次例外不应该再开——应该把这段逻辑搬出去。**

## 五、Ultralytics 怎么做同一件事

### 5.1 它**没有**插件系统（这一条要说清楚）

搜索结论（可复核）：

```
$ grep -rn "entry_points\|pluggy" ultralytics/ pyproject.toml     → 0 处
$ grep -rn "importlib.metadata" ultralytics/                      → 仅用于读 torchvision 版本号
```

没有 `entry_points`、没有 `pluggy`、没有 importlib 目录扫描。
**Ultralytics 的"扩展"全部是"改源码 + 注册进清单"**，和我们印象里的"插件系统"不是一回事。
它真正接近插件的是**回调（callback）机制**。

### 5.2 它的"模块 ↔ 算法"契约：**一份 YAML + 三条约定**

一个模块要被网络用上，只做三件事（`AGENTS.md:94` 原文）：

> New layer → the matching module under `nn/modules/`, export it from `nn/modules/__init__.py`,
> import it into `nn/tasks.py` so `parse_model` can resolve it, and touch `base_modules`/`repeat_modules`
> only if the layer needs channel or repeat handling.

**注意：这和驭臂加算法一样，也是要改源码的**（`__init__.py` + `tasks.py`）。
所以"Ultralytics 加模块不用改代码"是个误解——**它改的是 import，不是列表**。
真正的差别在**注册之后的表达能力**：

| | 驭臂 | Ultralytics |
|---|---|---|
| 注册动作 | import 类 + 在列表里 `实例化()` | import 类（无实例化） |
| 注册之后 | 算法**立刻生效**（无条件执行） | 算法只是**可被引用**，是否使用由 YAML 决定 |
| 组合方式 | 列表顺序 = 执行顺序，后者覆盖前者的 `ctrl[:]` | YAML 声明数据流：`[from, repeats, module, args]` |
| 参数来源 | 插件类属性（改代码才能改） | YAML `args` + `cfg/default.yaml` |
| 规模参数 | 无 | `scales`（depth/width/max_channels）三档缩放 |

网络拓扑是**声明式**的（`cfg/models/11/yolo11.yaml`）：

```yaml
backbone:
  # [from, repeats, module, args]
  - [-1, 1, Conv, [64, 3, 2]]      # 0-P1/2
  - [-1, 2, C3k2, [256, False, 0.25]]
  - [-1, 1, SPPF, [1024, 5]]       # 9
  - [-1, 2, C2PSA, [1024]]         # 10
```

模块名解析（`nn/tasks.py:2100-2106`）：

```python
m = (
    getattr(torch.nn, m[3:]) if m.startswith("nn.")
    else getattr(__import__("torchvision").ops, m[16:]) if m.startswith("torchvision.ops.")
    else globals()[m]                       # ← 按名字在同名空间里找类
)
if restricted and not (isinstance(m, type) and issubclass(m, torch.nn.Module)):
    raise TypeError(emoji(f"ERROR ❌️ module '{m}' is not a permitted model layer under restricted loading."))
```

`globals()[m]` 是纯隐式解析（改个类名，YAML 就找不到），
所以它配了个 `restricted` 模式 + 明确的 `TypeError`——**隐式机制必须配显式检查**，这条经验对驭臂直接适用。

### 5.3 它的"算法 ↔ 模型"契约：**声明在文件里，不靠人记**

这是一个模型 YAML 的全部"契约"（`cfg/models/11/yolo11.yaml:8-16`）：

```yaml
nc: 80          # number of classes
scales:         # [depth, width, max_channels]
  n: [0.50, 0.25, 1024]
```

而运行期参数集中在 `cfg/default.yaml`，**每个字段都带类型和取值说明**：

```yaml
imgsz: 640   # (int | list) train/val use int (square); predict/export may use [h,w]
batch: 16    # (int | float) batch size as int (e.g. 16), -1 for AutoBatch, or float in (0.0, 1.0)
device:      # (int | str | list) device: 0/[0,1] CUDA, 'npu:0' Ascend, 'xpu:0' Intel, 'cpu'/'mps', -1/[-1,-1] auto GPUs
```

**要对照的关键点**：Ultralytics 的模型/配置把"**这份配置要求什么**"
（`nc`、`imgsz`、`kpt_shape`）写进了**文件本身**；
而驭臂的模型库写了 `自由度`、`执行器数`（客观事实），
却**没写"这个模型需要算法满足什么"**（主观约束）——差别就在这里。

任务与求解器的绑定也是一张显式注册表（`models/yolo/model.py:99-115`）：

```python
def task_map(self) -> dict[str, dict[str, Any]]:
    return {
        "classify": {"model": ClassificationModel, "trainer": ..., "validator": ..., "predictor": ...},
        "detect":   {"model": DetectionModel,      "trainer": ..., "validator": ..., "predictor": ...},
        ...
    }
```

任务能不能被自动认出来，靠 `guess_model_task()`（`nn/tasks.py:2259-2305`）——
**从 YAML 最后一个 head 模块名反推**（可复核）：

```python
def cfg2task(cfg):
    m = cfg["head"][-1][-2].lower()      # output module name
    if "detect" in m: return "detect"
    if "segment" in m: return "segment"
    ...
```

注意这正是 `globals()[m]` 那套隐式约定的**下游用途**：模块名既是注册键，
也是任务推断依据。**改一个模块名会同时影响解析和任务识别**——隐式约定的代价，它自己没完全消除。

### 5.4 它最像插件系统的地方：回调（callback）

`ultralytics/utils/callbacks/base.py` 的 `default_callbacks` 是一个 **25 个事件名 → 处理函数列表** 的字典（`:121-151`，
Trainer 14 个 / Validator 4 个 / Predictor 5 个 / Exporter 2 个）。

**一个直接可用的教训**：调用链里实际出现了 **26 个**事件名——`trainer.py:613` 调用了
`self.run_callbacks("on_batch_end")`，而 `"on_batch_end"` **不在 `default_callbacks` 里**（本机核实：
`'on_batch_end' in ev → False`）。因为调用处是 `self.callbacks.get(event, [])`，
**这个事件名今天永远是静默 no-op**。事件名拼错不报错——这正是"隐式扩展点"的代价，
和驭臂要避免的是同一个坑。

运行器（`engine/trainer.py:223-226`）的调用处**极简**：

```python
def run_callbacks(self, event: str):
    """Run all existing callbacks associated with a particular event."""
    for callback in self.callbacks.get(event, []):
        callback(self)
```

第三方集成（wandb / comet / mlflow / clearml / tensorboard / dvc / neptune / ray / hub / ax）
就是通过 `add_integration_callbacks(instance)` **挂到这个 dict 上**，
从而做到"**不改训练循环就接入一个平台**"。这和驭臂 `@每步` 的思路同源。

但**它的"不改核心"是有水分的**：`add_integration_callbacks` 本身是一张
**硬编码白名单**（`base.py:191-200` 逐个 `from .wb import callbacks as wb_cb` …），
而且它用**类名字符串**决定加载哪些集成：

```python
if "Trainer" in instance.__class__.__name__:        # base.py:190 ← 按类名字符串分支
```

新增一个官方级集成，仍然必须改 `base.py`（详见 5.5 的配方表）。

三个关键差别：

| | Ultralytics 回调 | 驭臂 安全注册表 |
|---|---|---|
| 出错隔离 | ❌ 无 try/except（4 处 `run_callbacks` 全是裸循环：`trainer.py:225`、`validator.py:367`、`predictor.py:553`、`exporter.py:1821`），一个回调抛异常 = 整轮训练失败 | ✅ 逐个隔离 + 停用 |
| 消息消费 | ❌ 无"拦截"语义，所有回调都跑 | ✅ 返回 `True` 可吃掉消息（`插件系统.py:81`） |
| 运行期装卸 | ✅ `self.callbacks` 是普通 dict，随时可加 | ❌ 插件只能在启动时定；`加插件()` 只给外壳内部用 |
| 事件数量 | **25 个具名生命周期事件**（另有 1 个未注册却被调用的 `on_batch_end`） | **1 个通用 `每步` + 5 个拉取钩子** |

**25 vs 1** 是这份对比里最值得记住的数字：
Ultralytics 用**丰富的具名事件**换来了"能挂很多种扩展"；
驭臂用**一个通用每步**换来了"简单、好教"。前者可扩展性强，后者学习成本低——
对驭臂当前阶段（教学 + 单人开发）后者未必是错的选择，但**至少应该知道自己在放弃什么**。

### 5.5 四条经核实的设计事实（都是"隐式"的代价）

这四条是本报告在核对源码时逐条验证的，它们共同说明**为什么驭臂不该照抄 Ultralytics 的注册方式**：

**① `TASK_MAP` 这个字典不存在。** 它是 `Model` 上的一个 **property**：
基类 `engine/model.py:1194` `raise NotImplementedError("Please provide task map for your model!")`，
`YOLO` 在 `models/yolo/model.py:98-147` 实现 `task_map`，
消费点 `Model._smart_load(key)`（`engine/model.py:1165-1188`）用 `except Exception` 把
`KeyError`/`TypeError` 统一翻译成 `NotImplementedError`——**少数做了错误翻译的地方**。

**② 基础执行器永远只传一个参数。** `BaseModel._predict_once`（`tasks.py:198`）是 `x = m(x)`。
真正的双输入 `(x, y)` **只存在于任务专用 `predict()` 覆写里的硬编码 `isinstance` 名单**：

```python
# tasks.py:1184-1192（WorldModel.predict）
if isinstance(m, C2fAttn):              x = m(x, txt_feats)
elif isinstance(m, WorldDetect):        x = m(x, ori_txt_feats)
elif isinstance(m, ImagePoolingAttn):   txt_feats = m(x, txt_feats)
else:                                   x = m(x)
```

**新增一个双输入模块，除了改模块定义和 `parse_model`，还要再改这串 `isinstance` 链。**
对比驭臂：`安全注册表._单独派发` 用 `issubclass(type(消息), info.message_type)` **按类型标注自动匹配**
——**驭臂在这里无意中做对了 Ultralytics 做错的事**（消息类型 ↔ 处理器的绑定是自动的，不需要维护名单）。

**③ 未知模块名是"裸 KeyError"，未知输出通道是"静默假设"。**

```python
# tasks.py:2104-2110
m = (... else globals()[m])     # ← 名字打错 → 裸 KeyError，无 try/except、无候选建议
# tasks.py:2201-2202
else:
    c2 = ch[f]                  # ← 未知模块 → 静默假设"输出通道 == 输入通道"
```

官方只能把这个 `KeyError` 写进文档 FAQ（`docs/en/guides/model-yaml-config.md:397`：
`KeyError: 'ModuleName' → Module not imported → Add to tasks.py imports`）。
**这是"隐式机制不配显式校验"的最坏结果**：错误要么毫无提示（`KeyError`），
要么推迟到 forward 里炸成 shape mismatch（`c2 = ch[f]`）。

**④ 可扩展性与安全性在它这里是互斥的。** `parse_model` 只在受限加载模式下做类型校验
（`tasks.py:2111-2113`），该模式由 `ULTRALYTICS_SAFE_LOAD` 开关控制，**默认关闭**。也就是说：

> 要么允许 `globals()` 取任意名字（可扩展、不安全），
> 要么只允许白名单里的 `nn.Module` 子类（安全、不可扩展）。两者不可兼得。

**驭臂要警惕同一个取舍**：今天驭臂是"完全信任插件目录里的代码"。
这在单人本地开发下是合理的，但值得**显式写下来**（"我们选择了可扩展性，因此插件目录视为可信代码"），
而不是默认它不存在这个问题。

**配方式对比（"加一个东西要改几处"）**：

| 想加什么 | Ultralytics 改几处 | 驭臂改几处 |
|---|---|---|
| 一个新模块/新层 | **3 处必需**（`nn/modules/xx.py` + `__init__.py` + `tasks.py` 的 import）+ 1 处推荐（`base_modules`）；双输入模块再 +1 | **2 处**（`plugins/xx.py` + `主程序.py` 的 import 与列表） |
| 一个新任务 | **约 8–9 处**（head / Model / `guess_model_task` / 三件套 / `task_map` / `TASKS` 等五张表 / YAML） | 不适用（驭臂只有一类任务） |
| 一个官方级集成回调 | **3 处**（新模块 + `base.py` 白名单 + settings 且必须升 schema 版本号） | 不适用 |

> ⚠️ 最后一行那个"必须升 schema 版本号"值得一提：`utils/__init__.py:1393` 的 settings 版本是 `"0.0.8"`，
> 加一个键而不升版本，`_validate_settings`（`:1440-1446`）会**重置用户的全部设置**。
> 这是"注册清单漏一项就静默破坏用户数据"的真实案例——正是驭臂 `AGENTS.md` 该防的那类事。

### 5.6 参数校验：写错一个键名会得到"带拼写建议"的错误

`ultralytics/cfg/__init__.py` 把参数按类型分成三组 `CFG_FLOAT_KEYS` / `CFG_INT_KEYS` / `CFG_BOOL_KEYS`（`:202/:252/:276`），
并用 `check_dict_alignment()`（`:622-666`）做键名对齐检查。关键在它**怎么报错**：

```python
if mismatched := [k for k in custom_keys if k not in base_keys and k not in allowed_custom_keys]:
    from difflib import get_close_matches
    for x in mismatched:
        matches = get_close_matches(x, base_keys)          # ← 拼写相似度匹配
        match_str = f"Similar arguments are i.e. {matches}." if matches else ""
        string += f"'{colorstr('red', 'bold', x)}' is not a valid YOLO argument. {match_str}\n"
    raise SyntaxError(string) from e
```

写 `epoch=100`（少个 s）会得到 `'epoch' is not a valid YOLO argument. Similar arguments are i.e. ['epochs=100'].`
——**不是静默忽略，而是猜出你想写什么**。

**这条对驭臂的直接价值**：`设置参数()` 今天对不存在的参数名返回
`f"插件 {类名} 没有参数「{名}」"`（`插件系统.py:115`）——已经是好错误了，
但可以再加一句 `difflib.get_close_matches` 的拼写建议，成本 3 行，
收益是"滑杆串了插件名"这类问题一眼可诊断。

**更普适的经验**：**隐式契约的代价，可以用"好的报错"来偿还**。
Ultralytics 的模块名解析（`globals()[m]`）和键名解析都是隐式的，
但它给每条隐式路径都配了一句"你是不是想写 X"。驭臂的隐式约定比它更多，
却还没有这种报错——这正是 P0-1 / P1-1 要达到的效果。

## 六、逐项对比

| 维度 | 驭臂 | Ultralytics 8.4.160 | 判断 |
|---|---|---|---|
| **扩展单元** | 控制插件（算法）/ 面板（UI） | 模块（层）+ 集成回调 | 驭臂的单元更"整"，一个插件 = 一个完整算法 |
| **发现方式** | 算法：硬编码列表（改 `主程序.py`）<br>面板：**目录扫描**（放文件即生效） | 模块：import 进 `__init__.py` + `tasks.py`<br>回调：程序化 `add_callback` | ⚠️ 驭臂内部不一致；**面板那套更先进** |
| **注册之后** | 立刻生效、无条件执行 | 只是"可被引用"，生效由 YAML 决定 | ⚠️ 驭臂缺"声明式组合"这一层 |
| **契约载体** | 5 个桥接文件里的注释 + `hasattr` 探测 | YAML + `AGENTS.md` 扩展清单 + 类型注解 | ❌ **驭臂最大的短板** |
| **契约可机检** | 对官方的 21 项 ✅；对插件自身 ❌ | ❌（`globals()[m]` 纯隐式，靠 code review） | 驭臂有更好的**方法论**，只是没用到自己身上 |
| **算法↔模型匹配** | 无声明、无预检 → **静默停用**（有事故） | YAML 里声明 `nc`/`kpt_shape`/`ch`，不匹配直接抛 `ValueError` | ❌ 驭臂明确落后 |
| **出错隔离** | ✅ 逐个隔离 + 停用 + 中文定位 | ❌ 无 | ✅ **驭臂领先** |
| **错误恢复** | ❌ 累计 2 次永久停用，无冷却/重试 | N/A（直接失败退出） | 各有代价；见改进 P0-2 |
| **运行期热切换** | ✅ 换模型 + 重绑 + 通知插件 | ❌ 换模型 = 新起一次 | ✅ **驭臂领先** |
| **参数系统** | 类属性 + 滑杆 + `范围`（UI 侧钳制） | `cfg/default.yaml` + 类型校验 + `CFG_*_KEYS` | ⚠️ 驭臂缺类型/边界校验（见 P2-1） |
| **版本与清单** | 三道：`requirements.lock` + 21 项接口 + `外壳指纹.json` | `pyproject.toml` 注释 + `__version__` 自动发版 | ✅ **驭臂更贴题** |
| **失败信息** | 中文人话 + "该改哪个文件" | `LOGGER` + emoji 前缀；参数键名有 `difflib` 拼写建议 | ✅ **驭臂更友好**（面向自己/学生）；拼写建议值得借（见 P2-1） |

## 七、值得学习的经验（六条）

### 经验 1：显式注册清单 + "漏一个都不行"的意识

Ultralytics 的 `AGENTS.md:96` 把"加一个可训练任务"要动的地方**一条不落**列出来：

> 新增可训练任务 → `TASKS`、`TASK2DATA`、`TASK2CALIBRATIONDATA`、`TASK2MODEL`、`TASK2METRIC`；
> 还要看 `guess_model_task()`、`build_yolo_dataset()`、`Results` 类型。

**学什么**：不是学它的清单内容，而是学"**把跨文件注册点当成一个显式契约来维护**"。
驭臂的 10 个插件钩子正需要这样一张表（见 P0-1）。

### 经验 2：目录扫描 / 约定优于配置

Ultralytics 的模块靠"文件放对位置 + import 进 `__init__.py`"被发现。
**这条驭臂的面板子系统已经做到了，而且更彻底**（连 `__init__.py` 都不用改）。
值得学的不是"照搬"，而是**把已经在面板上验证过的机制推广到算法层**——
同一项目内统一标准，比引入新机制更划算。

### 经验 3：扩展边界要写出来（"不要 fork 引擎"）

`AGENTS.md:100-102` 的 **Extension boundaries**：

> Subclass the task-neutral engine and override hooks; **do not fork training or prediction loops.**
> Keep format-specific export behavior in `ultralytics/utils/export/` and bind it at export time;
> **do not add `self.format` branches to `nn/modules/head.py`.**

**学什么**：这句话直接回答了驭臂的一个现存冲突——"改进模型切换"要不要动 `启动.py`？
答案应该是"**不许 fork 外壳主循环，要扩展就扩展桥**"。
驭臂需要用同样的措辞写下自己的 Extension boundaries，否则每次改进都会面临"要不要破哈希"的纠结。

### 经验 4：隐式机制必须配显式校验（并且要给出可操作的报错）

`globals()[m]` 是隐式的，所以 Ultralytics 配了：

```python
if restricted and not (isinstance(m, type) and issubclass(m, torch.nn.Module)):
    raise TypeError(emoji(f"ERROR ❌️ module '{m}' is not a permitted model layer under restricted loading."))
```

**学什么**：驭臂的隐式约定更多（`面板类`、`名称`、`可调参数`、`模型已切换`…），
但**一个显式校验都没有**。这正是 P1-1（插件自检）要补的。

### 经验 5：Where to look —— 文档的价值在"故障定位"而不是"功能介绍"

`AGENTS.md:86-98` 的 Where to look 全是**症状 → 文件**：

> - Wrong mAP/metrics or val output → `engine/validator.py`, `models/yolo/<task>/val.py`, `utils/metrics.py`
> - Download or asset failures → `utils/downloads.py`, `utils/checks.py` `check_file`

**学什么**：驭臂的 `★ 踩过的坑` 注释内容质量极高（比如"面板上只能显示 ASCII"、
"`ux.setup_theme()` 必须在 ImGui 上下文就绪后调用，否则段错误"），
但它们**埋在各个文件头部**，每次开新会话都要重新发现。
把它们抽成一张"症状 → 文件 → 自检命令"表，成本 1 小时，收益持续。

### 经验 6：数据契约要写进数据文件本身

Ultralytics 把"这份配置要求什么"写进 YAML（`nc`、`kpt_shape`、`imgsz`）；
驭臂的 `模型库.json` 只写"这个模型是什么"（自由度、执行器数、许可），
**不写"这个模型要求算法满足什么"**（需要几个执行器、末端 site 叫什么、可辨识哪些连杆）。

**学什么**：把约束从"人的记忆"移进"数据文件"，是所有自动化预检的前提（见 P0-3）。

### 🔴 P0-2：修掉"插件被永久停用"的不可恢复性（真实事故的直接成因）

**问题**：`插件系统.py:231-253` 的错误计数**只增不减**，第二次出错即永久停用；
且**插件状态里的"停用"不会因为换了合适的模型而复原**。日志已证明后果：切回可用的 UR5e 也不动了。

**改法（三处小改，按优先级）**：

1. **加冷却/重试**（最小改动，`_处理异常` 内）：

   ```python
   # 连续出错 → 停用；但允许"恢复窗口"：换模型 / 用户点"重试" 时清零
   def 重置(self, 名: str | None = None) -> None:
       """清掉出错计数与停用状态。换模型成功后由外壳调用。"""
   ```
2. **在模型切换成功处调用 `注册表.重置()`**（`启动.py:141` 附近，`if 路径:` 之前）：
   语义正确——换了模型就是换了环境，旧环境的错误不该延续。
3. **把"为什么停用"暴露到界面**：今天只打印在终端。`模型库面板`/`监控面板` 增加一行
   "算法状态：关节 PD 已停用（原因：维度不匹配 7≠6，可点重试）"。

**成本**：约 1.5 小时。**验收**：复现日志场景（7 轴 → 6 轴 → 切回 6 轴），控制器应自动恢复工作。

### 🟠 P1-2：把 handler 表建一次（实测省 ≈ 20 µs/轮）

```python
def __init__(self, 插件列表):
    ...
```

### 🟡 P2-1：`设置参数()` 补类型与边界校验

**问题**：`插件系统.py:112-120` 是 `setattr(self, 名, float(值))`——

## 九、明确**不建议**照抄的部分

| Ultralytics 的做法 | 为什么驭臂不该抄 |
|---|---|
| `globals()[m]` 名字解析（改类名即静默失效） | 它自己都得靠 `restricted` 模式 + `TypeError` 兜底。驭臂应走**显式清单 + 目录扫描**，而不是字符串解析全局命名空间 |
| `run_callbacks` 不做出错隔离 | 对 6 小时离线训练是"快速失败"，对**开着窗口、用户在看的实时仿真**是灾难。驭臂的隔离必须保留 |
| 25 个回调事件全量照搬 | 驭臂只有一个执行阶段（每步），照搬会产生大量空事件。**按需加 3 个**（见 P2-2） |
| `nn/tasks.py` 单文件 2344 行 | 那是"模块解析 + 模型装配 + 任务推断 + 损失"全塞一起的结果。驭臂 `插件系统.py` 366 行是健康体量，别学它膨胀 |
| `TaskMap` 的 5 个并行注册表（`TASKS`/`TASK2DATA`/…） | 那是 8 种任务 × 多平台才需要的复杂度。驭臂 1 种任务（关节力矩控制），**平行清单只会增加漏登记的 chance** |
| 每天 1–2 个版本、无人值守发版 | 见 `工程化管理_参考Ultralytics.md` 第五节的已有结论；本报告不重复 |

## 附：一句话回答你最初的问题

> **"他们这个项目是不是也有一个类似于我们的插件系统？"**

**没有。Ultralytics 没有插件系统**——没有 `entry_points`、没有 `pluggy`、没有目录扫描。
它有**注册表 + 约定**（模块靠名字进 `globals()`、配置靠 YAML）和**回调钩子**（25 个生命周期事件）。
真正可比的不是"有没有插件系统"，而是两件事：

1. **"模块 ↔ 算法"的契约写在哪里**——它写在 YAML 和 `AGENTS.md` 的扩展清单里（**显式、可读、可 review**）；
   驭臂写在 5 个桥接文件的注释和 `hasattr` 探测里（**隐式、易漏、无自检**）。
2. **"算法 ↔ 模型"怎么保证对得上**——它把要求写进配置文件（`nc`/`kpt_shape`/`ch`），
   不匹配就 `ValueError`；驭臂不写、不查，不匹配就**静默停用插件**（已在日志里发生）。

**驭臂真正的优势在别处**：出错隔离、可机检的接口边界、热切换模型——
这三条 Ultralytics 一条都没有。**所以正确的姿态不是"学它"，而是：
用它"契约显式化"的习惯，去补强驭臂"机制更先进但契约没写下来"的短板。**
