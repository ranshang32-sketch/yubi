## 三、技术可行性（逐项，附官方代码证据）

### 3.1 模型是怎么进到窗口里的

整条链路只有一个入口：**仿真侧发 `messages.ModelEvent`**。

```
仿真侧                                窗口侧
MjModel.from_xml_path(路径)
   └─ ViewerHandle.send_to_viewer(ModelEvent(model, path))
                              │
                              ▼
                    Viewer._on_model(event)           viewer_protocol.py:211
                      └─ load_model(): 深拷贝模型 + 新建 MjData + mj_forward
                    ViewerApp._on_model(event)        viewer_app.py:485
                      └─ _reset_app_state()（清掉界面上的旧状态）
                    StepControl._on_model(event)      step_control.py:33
                      └─ 新建 sim.StepControl()（"让新模型从时间同步开始"）
```

**这就是"热切换"的全部机制** —— 官方注释写得很直白：

> `viewer_handle.py:127`：*"The updated model and data; rebind both, they may be new objects (e.g. after the viewer sends a ModelEvent)."*

也就是说：**换模型 = 再发一条 `ModelEvent`**，不需要重启、不需要重建窗口。

### 3.2 官方已经内建了"拖文件进窗口"

`viewer_app.py:253-271`（`update()` 里）：

```python
drop_file = self.viewer.get_drop_file()
if drop_file:
    data = parser.parse(drop_file)                  # 官方加载器
    if data is not None:
        self.viewer.send_to_sim(ModelEvent(model=data.model, path=drop_file))   # 通知仿真侧
        self.viewer.dispatch(ModelEvent(model=data.model, path=drop_file))      # 通知窗口侧
        self.viewer.get_sim_snapshots()             # 丢掉旧的过期快照
```

`parser.parse()`（`parser.py:19-33`）支持 `.xml` / `.mjb` / `.mjz`（含 zip 资产）。

**所以"从本地导入模型"这件事，官方 UI 层面已经支持了 —— 用户现在就可以把 XML 拖进窗口。**（不过在驭臂里拖了会出问题，见 4.1。）

### 3.3 "打开文件"对话框：官方没有，但可以补

- 官方 `File` 菜单实测只有 `Quit` 一项（`viewer_app.py`）
- mujoco 的 Python 层**没有**暴露原生文件选择器（grep 不到 tinyfd / OpenFile 之类）

**替代方案（推荐）**：调 macOS 原生选择器，一行就够：

```python
subprocess.run(["osascript", "-e",
    'POSIX path of (choose file with prompt "选择模型" of type {"xml","mjb","mjz"})'],
    capture_output=True, text=True)
```

这与项目已有的做法一致（启动器脚本就是用 `osascript display dialog` 弹中文提示的），零新依赖。

### 3.4 能不能"空白启动"

能。喂一个"只有地面和灯"的 MJCF 即可（`nq=nv=nu=0`）。窗口、面板、19 个官方面板都能正常工作。

**但**：空白场景下默认插件会崩 —— 见 4.2（已实测）。

## 四、必须先修的 3 个坑

### 4.1 我们的外壳绕过了 `sync()`，所以拖拽换模型**只换了一半**

这是最关键的发现。

官方推荐的仿真循环是 `handle.sync(plugins=注册表)`，它内部会派发 viewer 事件给插件。而**我们的 `启动.py` 为了做出错隔离，把 `sync()` 拆开自己写**（`启动.py:118-134`）：

```python
for 事件 in 仿真端点.get_viewer_events():
    注册表.处理消息(事件)          # ← 事件进的是"我们的注册表"
```

我们的注册表 = `[StepControl, *你的插件, 参数应用器]` —— **里面没有 `ViewerHandle`**。

后果：用户在窗口里拖进一个模型 → 窗口侧 `Viewer.dispatch()` 把**窗口自己的** model/data 换掉了（画面变了），但**仿真侧的 `model`/`data` 没人接** → 物理和控制还在旧模型上跑 → **画面和物理不一致**。

**修法**：在仿真循环里显式处理 `ModelEvent`，做官方 `ViewerHandle._on_model` 那三件事，再加我们自己的善后：

```python
@messages.handler
def 换模型(self, event: messages.ModelEvent) -> bool:
    句柄.model = event.model
    句柄.data  = mujoco.MjData(event.model)
    mujoco.mj_forward(句柄.model, 句柄.data)
    插件框架.通知模型加载(插件列表, 句柄.model, 句柄.data)   # 让插件重新拿 model/data
    # 参数桥/辨识桥要重建（它们缓存了旧的模型引用与参数表）
    return False
```

工作量：小（约 20 行），但**动的是 `启动.py`（核心文件）**，改完要刷新 `零改动自检` 的基准。

### 4.2 空场景会把默认控制插件"弄停用"（已实测复现）

实测：加载一个只有地面的场景（`nq=nv=nu=0`），派发 3 次 `StepEvent`：

```
空场景: nq=0 nv=0 nu=0 nbody=1
⚠ 插件【关节 PD 位置控制】出错（已隔离，软件继续运行）：IndexError: index 1 is out of bounds for axis 0 with size 0
  出错位置：关节pd控制.py 第 73 行（每步控制）
✗ 插件【关节 PD 位置控制】再次出错 → 已停用。其他插件和界面不受影响。
  派发 3 次后 → 已停用: {'关节 PD 位置控制'}
```

出错的是 `plugins/关节pd控制.py:73` 的 `目标[1] += 0.35`（"抬臂"演示动作）—— 空场景没有关节，索引 1 越界。

**注意**：出错隔离机制本身工作正常（软件没挂）。但插件被**停用**了，于是用户之后选一个真模型进来，**机械臂不会被控制**（插件已经停用，只能重启）。

**修法**：给插件加一行保护（`if len(数据.qpos) >= 3:`），或者让外壳在 `nu==0` 时不派发 `StepEvent` 给控制插件。推荐前者（更稳，也顺手修了一个潜在 bug）。

### 4.3 参数辨识插件写死了 UR5e 的连杆名

`plugins/参数辨识插件.py` 的 `默认可辨识` 表里是 UR5e 的 body 名：

```python
("forearm_mass",  ("forearm_link",   "mass"), 1.98, (0.3, 6.0)),
("upperarm_mass", ("upper_arm_link", "mass"), 8.393, (1.0, 20.0)),
("wrist_mass",    ("wrist_1_link",   "mass"), 1.4,  (0.2, 4.0)),
```

实测各模型的连杆名完全不同：

| 模型 | 连杆名 |
|---|---|
| universal_robots_ur5e / ur10e | `base, shoulder_link, upper_arm_link, forearm_link, wrist_1_link, wrist_2_link, wrist_3_link` |
| franka_emika_panda | `link0…link7, attachment` |
| kuka_iiwa_14 | `base, link1…link7` |
| ufactory_xarm7 | `link_base, link1…link7` |

后果：换成非 UR 模型后点"辨识"会失败（异常被兜住，但界面会显示"没有改善"，用户会困惑）。

**修法**：给它一张"每个模型辨识哪些连杆"的表（放在 `模型/模型库.json` 里），模型一换就跟着换；表里没有的模型就**在界面上明确说"该模型暂不支持辨识"**，而不是假装跑了一遍。

### 4.4 已经确认**不受影响**的地方（好消息）

| 项 | 结论 |
|---|---|
| 任务空间控制插件 `末端两点运动.py` | ✅ **不用改** —— 实测 5 个模型的末端站点**都叫 `attachment_site`** |
| `指标桥` / `参数桥` / `曲线面板` | ✅ 与模型无关（按插件名索引） |
| 监控/录制/参数面板 | ✅ 与模型无关 |
| 官方 19 个面板 | ✅ 官方本来就支持换模型（这就是它们的 `_on_model` 存在的原因） |

## 五、同类软件是怎么做的（官方文档比对）

| 软件 | 启动时 | 选模型的入口 | 本地模型 | 运行中切换 |
|---|---|---|---|---|

| **PyBullet** | 无 GUI 概念 | ❌ 没有模型浏览器，全靠代码 `p.loadURDF()` | 代码 | 代码 |

### 归纳出来的 4 种通行范式

1. **空场景 + 浏览器面板**（Gazebo / Isaac / CoppeliaSim / Webots 全都是这个）
   —— 启动给一个空世界，模型从侧边面板里挑、拖进场景。
2. **内置模型库 + 用户可扩展**（CoppeliaSim 的 Model Browser、Gazebo 的本地资源路径）
   —— 库里有一批开箱可用的模型，用户还能往里加。
3. **文件导入**（所有人都有）
   —— File→Open / Import 向导 / 原生文件选择器。
4. **拖拽**（simulate / CoppeliaSim / Isaac）
   —— 把文件从 Finder 拖进窗口。

> **驭臂该照哪条走？** 你的需求 = 范式 1 + 2 + 3 的组合，而这**恰好是四家成熟软件的共同做法**，不是偏门设计。而且官方底座已经把最难的"热切换"和"拖拽"做完了，我们只需要补"面板"和"文件选择器"。

## 六、三个方案（含推荐）

### 方案 A：最小改动 —— 只加"模型库"面板（推荐，先做这个）

```
启动  →  空场景（只有地面+灯）
窗口  →  右侧出现【模型库】面板：
          ┌─────────────────────────────────────┐
          │ 模型库                                │
          │ ○ Universal Robots UR5e   6轴 BSD     │
          │ ○ Universal Robots UR10e  6轴 BSD     │
          │ ● Franka Emika Panda      7轴 Apache  │  ← 点一下即切换（当前项用 ● 标出）
          │ ○ KUKA LBR iiwa 14        7轴 BSD     │
          │ ○ xArm7                   7轴 BSD     │
          │ ─────────────────────────────────── │
          │ [从本地导入模型…]   ← 调 macOS 原生选择器 │
          │ [重新加载当前模型]                     │
          │ 提示：也可以把 .xml 直接拖进窗口          │
          └─────────────────────────────────────┘
```

- 数据源：`模型/模型库.json`（**已经生成好了**）
- 切换：面板发一条 `换模型命令` → 仿真侧加载 XML → 发 `ModelEvent`
- 导入：`osascript choose file` → 拿到路径 → 同上
- 一句话总结：**不新建任何"启动页/对话框"，就用一个面板把 1~4 全满足**

**优点**：改动集中（1 个新面板 + 1 个新桥 + 4.1/4.2/4.3 的修复）；风格与现有 5 个面板一致；随时可关掉（复用刚做的 × / F9 机制）。
**缺点**：不是"启动引导式"体验 —— 一进来是空场景 + 一个面板，而不是弹窗问你"要打开什么"。

### 方案 B：方案 A + 启动欢迎对话框

在 A 的基础上，空场景下用 ImGui 弹一个**模态欢迎框**（"从模型库选择 / 从本地导入 / 空白场景"），选完就关掉。

**优点**：最接近你说的"点开软件先给几个选项"。
**缺点**：官方 `configure_docking_layout` 没给模态框的位置，模态框会挡住 3D 视图；而且**面板被关掉后就没法再叫出来**（要靠 F9 那套）。**建议：如果要做，做成"上次没选模型时才显示一次"，且提供"不再显示"**。

### 方案 C：完全照 Gazebo —— 空世界 + 独立"资源浏览器"+ 拖拽

把模型库做成可搜索、带缩略图、支持分类与拖拽的完整资源浏览器。

**优点**：最像成熟软件。
**缺点**：要生成缩略图（离屏渲染，成本高）、要做拖拽落点解析（官方 `get_drop_file` 只给路径，不给你"拖到哪个坐标"）。**投入产出比差，不建议现在做。**

### 推荐路线

> **先做方案 A，把"能选、能切、能导入"跑通并验收；跑顺了再决定要不要加方案 B 的欢迎框。**

理由：A 已经覆盖你提的全部 4 条需求，而且**风险最低**（不碰官方布局、不引入模态框这类难撤销的东西）。B 只是给 A 加一层"首次引导"的皮，随时可以后面补。

### 验收标准（沿用本项目的强度：不靠"看起来能跑"）

1. **切换**：在 5 个模型之间连续切换 3 轮，每次都满足——
   - 3D 视图显示的是新模型（不是旧的）
   - 终端里 `步数` 继续增长，误差收敛到 `< 1°`
   - 官方 19 个面板里的关节数、执行器数跟着变
2. **一致性**：切换后 `面板看到的模型 == 仿真侧物理用的模型`（用"改一个名字不同的模型，看关节数是否变化"来证伪）
3. **导入**：用原生选择器选一个**仓库外**的 XML → 能加载；选一个**坏 XML** → 有中文报错、**软件不崩、旧模型还在**
4. **空场景**：启动时不加载任何机械臂，窗口正常、面板正常、**没有插件被停用**
5. **回归**：`--自检` 21 项全绿；`零改动自检` 通过（改核心文件后刷新基准）；`验证参数辨识.py` 仍 1.47%
