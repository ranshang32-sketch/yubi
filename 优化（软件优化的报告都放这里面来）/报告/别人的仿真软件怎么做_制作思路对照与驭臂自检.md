# 别人的仿真软件是怎么做出来的 · 制作思路对照与驭臂自检

> 写作日期：2026-10-08 ｜ 对照对象：`~/Desktop/驭臂`（"小软件"，自有 Python **11 139 行**）
> 本文回答三个问题：
> ① 其他开源仿真软件各自的**制作思路**是什么？
> ② 驭臂的思路与之相比，**缺点在哪、能学什么**？
> ③ 为什么现在会觉得"迷茫"，以及下一步该定什么。
>
> 取证口径：本文所有关于驭臂的论断都用仓库实测（行数、git 历史、源码、探针输出）支撑；
> 所有关于外部项目的论断都标来源 URL。**分不清是实测还是推断的地方会明说。**
>

> 现已在 **§2.1【官方工作台派】** 补入，并据此修正了 §2.2、§3、§5.2、§7 的结论。**这是本报告最重要的一节。**

## 〇、直接给结论

### 0.1 一句话

**你的架构思路没有问题，自制流程的纪律甚至强于本文调研的大多数项目；
让你迷茫的不是"做得不好"，而是"一直在优化工具，却没有一个让工具长大的出口"。**

证据在后面，这里先给三条最硬的判断：

| 判断 | 依据 |
|---|---|
| **思路本身是对的** | 你独立选中的几条路（引擎当依赖、外壳可换、声明式装配、验证脚本化、错误隔离）正是主流项目验证过的路；其中"插件逐个隔离"你甚至补上了官方没有的 |
| **真正的结构性缺口只有一个** | 全部 6 个算法都是**关节空间/轨迹级**，没有一个带**任务成功判据、预算、失败语义**。缺了"任务"，这套东西永远只能演示，不能比较、不能积累 |
| **迷茫的来源是可定位的** | git 最近 22 次提交里 **12 次（55%）是界面细节返工**（抢焦点、页签校准、配色、落盘），而**只有 2 次（9%）是产品能力**；设计规格 §10 记着**同一天返工四轮**。精力在被"宿主框架没给你留位置"持续抽走，而不是在长产品 |

### 0.2 三条建议（按顺序）

1. **把"任务（Task）"立成一等公民** —— 这是把六个演示变成可比较、可积累、可被引用的东西的唯一开关。
2. **停止继续重建官方面板** —— 12/22 次（55%）提交是界面返工，而且**"让界面更灵活"正是 Studio 自己 Future Work 上的下一条**（§2.1）；改用"官方面板 + 我们只加自己的"混合形态，把界面投入冻结在维护档。
3. **给这个工具一个"被别人用"的出口** —— 要么开放（别人能用你的算法库），要么立标准（别人来跑你的任务）。没有出口的工具，做得再好也只会让人迷茫。

## 一、为什么要看别人怎么做

因为你现在的处境不是"技术不会"，而是"**做对了每一步，但说不清自己在造什么**"。

这件事在开源仿真软件的历史上反复出现过，而且已经有很清楚的解法分野。看别人怎么做，最大的价值不是抄功能，而是看清：

- **他们把"产品"这个词放在了哪一层**（放在引擎上？放在 GUI 上？放在任务/benchmark 上？）
- **他们明确拒绝做什么**（这一条比"做了什么"更能说明思路）
- **他们靠什么长大**（论文引用？别人依赖？模型库？排行榜？）

## 二、别人的制作思路（分类解剖）

> 每一类先给"这一类的赌注是什么"，再给成员。成员表里的"明确不做"列是重点。

> ★ **框选修正（2026-10-08，用户提问后补）**：本报告初版把 **MuJoCo Studio 降格成了"底座"**（当作 §4 的调研对象而不是 §2 的比较对象），
> 结果**漏掉了与驭臂最直接可比的那一类：引擎官方自己长出来的集成工作台**。
> 现补为 §2.1。初版把 MuJoCo 放在"图书馆派"也只说对了一半 —— 见 §2.1 的说明。

### 2.1 【官方工作台派】引擎作者自己长大成一个应用 ★与驭臂最直接可比

**赌注**：引擎已经赢了，接下来**把用户的工作流也占住** —— 从"别人程序里的库"变成"用户每天打开的那个窗口"。

| 项目 | 作者/归属 | 核心思路 | 关键表述 |
|---|---|---|---|
| **MuJoCo Studio** | Google DeepMind（引擎原厂） | 把老 `simulate` **重写成新应用**：UI 换 Dear ImGui，渲染换 Filament | 官方 README 原话：*"MuJoCo Studio is **the next iteration of the simulate application**. The UI has been **reimplemented** using Dear ImGui and the default renderer has been **switched to Filament**. The application is **still WIP**"* |
| **Gazebo**（现代版） | Open Robotics → 社区 | 从"仿真器"扩成"机器人仿真平台 + 生态" | 平台化 |
| **Webots** | Cyberbotics（商业公司，EDU 免费） | 完整 IDE 型仿真环境 | 唯一官方内置中文界面的（本仓调研结论） |
| **MuJoCo MPC (MJPC)** ★ | Google DeepMind | **不是仿真工作台，是"任务编写器"**：交互式预测控制框架 | README 定位：*"an **interactive application and software framework** for real-time predictive control"*、*"allows the user to **easily author and solve complex robotics tasks**"* |

#### ★ MJPC 是"任务该怎么做"的官方答案（本节比上面那张表更重要）

驭臂最缺的是"任务/判据"（§5.1）。而 **MJPC 恰好是官方在"任务"这一层的探索**，它的做法值得整段抄：

**它的设计思路是：不发明任务描述语言，而是复用引擎已有的"传感器"抽象。**

官方 OVERVIEW 原文：

> "Behaviors are designed by specifying a per-timestep cost …
> The residual **r** is a vector of elements that is **'small when the task is solved'**.
> **Residuals are implemented as custom MuJoCo sensors.**"

也就是说：

| 概念 | MJPC 的实现 | 用引擎的什么 |
|---|---|---|
| 任务目标 | **残差向量 r**（"任务解决时它趋近 0"） | MuJoCo **自定义 sensor** |
| 任务代价 | `l(x,u) = Σ wᵢ · nᵢ(rᵢ(x,u))` | 权重 + 范数 |
| 风险偏好 | `ρ(l,R) = (e^{RL}-1)/R`（R>0 保守、R<0 激进） | 一个标量参数 |

**为什么这对驭臂是好消息（而不是"又要学一套新东西"）**：

1. **它跟我们已有的东西同构** —— 驭臂已经有 `指标桥.py`（指标）、`参数辨识` 的残差思想、`录制` 的时序数据。
   **"任务成功"就是"残差落到阈值以下"**，不需要发明新的判据体系。
2. **它不要求新 DSL** —— 残差用引擎已有的自定义 sensor 表达，所以**算法作者仍然只写 Python**，符合驭臂"算法住在一个文件里"的既有形态。
3. **它天然可比较** —— 一旦任务是"残差 + 权重 + 范数"，两个算法在同一任务上的**代价曲线**就可以直接比大小，**这正是 §5.1 说的"能回答哪个更好"**。

→ **§7.1 的实现方式据此改写**：不要凭空设计 `成功判据` 字段，而是**引入"残差 + 权重 + 范数 + 阈值/预算"四件套**，残差从 `指标桥` 取。

**Studio 的制作思路，从它自己的 README 里能读出四条**（都是原文，不是我的推测）：

1. **先求连续，再求好** —— *"We have **ported the simulate UI** to make it **easier to users to switch**."*
   （把老界面先搬过来，让用户能平滑迁移；**ImGui 带来的新能力留到以后**。）
   → 这是**用户迁移优先**的产品决策，不是技术决策。
2. **明确自认未完成** —— *"The application is still WIP"*，并列出 **Future Work 三条**：
   ① Stability and Robustness（*"We need **user feedback** to find and fix bugs"*）
   ② UI/UX improvements（*"make use of the flexibility offered by Dear ImGui"*）
   ③ **Python integration**（*"As with simulate, we would like to make Studio usable via Python"*）
3. **对第三方扩展没有任何承诺** —— 全仓库 **没有一句**关于"第三方 GUI 扩展"的官方表述；`doc/programming/extension.rst` 只讲**引擎插件**（传感器/执行器/解码器/资源），不讲 GUI 插件。
4. **不写 changelog、不进文档** —— Studio 从未在 changelog 里公告过（本仓前份报告已核实）；包在 `experimental.` 命名空间下。

**★ 这条比前四类都重要，因为它同时是"最像你的项目"和"你最大的结构性风险"：**

| 维度 | Studio | 驭臂 |
|---|---|---|
| 形态 | 集成工作台（引擎 + 界面 + 面板 + 插件） | 集成工作台（引擎 + 自研面板 + 插件 + 项目） |
| 引擎 | **自有** | 借用（MuJoCo） |
| 分发 | 随 pip 包发行，人人可装 | 本机 `.app` |
| UI 定制度 | 受 ImGui 限制（Future Work ② 还没做） | **已做**（换肤、双语、侧栏、面板窗） |
| 插件机制的定位 | 有，但**实验性、无承诺** | 有，且**自己补了错误隔离 + 边界自检** |
| 中文界面 | ❌ 无（上游也没这个需求记录） | ✅ **有**（双语 + 字体补丁） |
| 任务/判据 | ❌ 无 | ❌ 无（见 §5.1） |

**读法（这是本报告最该被记住的一条）**：
> **你在跟一个"引擎原厂、随 pip 分发、还把'UI/UX 改进'和'Python 集成'写在待办清单上"的对手，竞争同一块地。**
>
> 它比你强的地方：**拥有引擎、拥有分发渠道、拥有上游话语权**。
> 它暂时不如你的地方，**恰好都写在它自己的 Future Work 里**：UI 灵活性、稳定性、Python 可用性。
> 而你手里它短期不会做的两样：**中文界面**、**面向具体实验的工作流（辨识/录制/项目快照）**。

**但这条推论必须说清楚**：Studio 的 Future Work ② 一旦做完（"make use of the flexibility offered by Dear ImGui"），
**你今天靠自己重写面板挣来的差异化，会被上游直接抹平** —— 因为它是原厂，改 `gui.cc` 比重建便宜得多。
**这就是为什么 §5.2 的建议是"把界面投入冻结在维护档"**：那不是省力，是**不在对手的主场下注**。

### 2.2 【图书馆派】把引擎做成别人依赖的库，明确不做应用

**赌注**：只要成为**别人程序里的一个依赖**，就永远有人用；一旦做成应用，就要跟所有做应用的人竞争。

| 项目 | 作者/归属 | 核心思路 | **明确不做** |
|---|---|---|---|
| **MuJoCo（引擎本体）** | Emo Todorov / Roboti LLC → Google DeepMind | 引擎即库；`mjModel`/`mjData` 分离，零运行时分配，可重配置计算管线 | **引擎层不做应用**。官方文档原话：可视化器"expects a generic window with an OpenGL rendering context, thereby allowing **users to adopt a GUI library of their choice**" |
| **pinocchio** ★ | 法国 Inria Willow 团队 | 只做刚体动力学算法（CRBA/RNEA/ABA），C++ 带 Python 绑定 | **不做 viewer**，官方文档第一行即拒绝：*"Pinocchio **does not feature a built-in viewer** and you will have to rely on external libraries."* |
| **Klampt** | Kris Hauser（单人/小组学术项目） | 只做运动学/规划算法库 | 不做产品化 GUI |

**★ 两条"官方主动砍掉 GUI"的硬证据（对驭臂的取舍最有参考价值）**：

1. **Drake 把自己的 GUI 删了。** commit `a6e1bb20`，标题 *"[workspace] Remove drake_visualizer"*，作者 **Jeremy Nimmer（Toyota Research Institute）**，日期 **2024-02-17** —— 补丁删掉 `tools/workspace/drake_visualizer/`，并改掉文档里所有引用。
   **一个由 MIT + 丰田研究院支持的项目，主动移除了自己的可视化前端。**
2. **pinocchio 从一开始就不做 viewer**，文档第一行就叫你去用别人的库。
3. **Jolt Physics 的作者写明这是"个人学习项目"**，且目标是 *"mainly be used for **games or VR simulations**"* —— **明确不服务机器人**。

**这三条合起来说明一件事**：在成熟项目里，**"要不要自己做 GUI"是一个被反复否决的选项**，而不是默认动作。
驭臂选了"自己做 GUI"，因此必须比它们多付一笔账 —— 这笔账在第 §5.2 已经量化（55% 的提交在界面）。
**关键不是"不该做"，而是"要知道这是一笔额外开销，且要有人替它买单"**（买单的方式见 §7.3 的出口）。

**给你的启示（已按 §2.1 修正）**：引擎本体确实**故意不做应用** —— 那句"让用户自选 GUI 库"说的是引擎层。
**但引擎原厂并没有停在那里** —— 它同时在做 Studio（§2.1）。所以准确的说法是：
**官方"引擎层开放、应用层自己吃"** —— 你可以寄生在它的引擎上，但它会亲自来抢应用层。

### 2.3 【引擎硬核派】从零写物理，以性能/精度立身

**赌注**：物理引擎是护城河，写好了就有十年寿命。

| 项目 | 作者/归属 | 核心思路 | 明确不做 |
|---|---|---|---|
| **Bullet / PyBullet** | Erwin Coumans（个人作者 → Google） | 游戏引擎级的碰撞检测；**给研究者一个免费快速的替代品**，Python API 极简（quickstart 导向） | PyBullet 不做精致 GUI（够调试就行） |
| **Jolt Physics** | Jorrit Rouwe（**一人作者**） | 为 3A 游戏做的工业级刚体引擎 | **不做 Python、不做 GUI、不做机器人专用** |
| **Chrono** | Alessandro Tasora / Dan Negrut（学术） | 通用多体+多物理（车辆、履带、颗粒） | 不做应用层 |
| **Rapier** | Sébastien Crozet / Dimforge（小团队） | Rust 优先、WASM 可跑、ECS 友好 | 不做编辑器（交给 Bevy 生态） |

**给你的启示**：这条路**单人也能走通**（Jolt 就是一个人），但代价是**十年只做一件事**，且**明确放弃应用层**。你已经有引擎了（MuJoCo），所以这条路对你是**反面教材**：不值得再投入一行到物理精度上。

### 2.4 【标准与生态派】引擎不自己写，靠"任务/接口"立标准

**赌注**：**标准比实现更值钱**。谁定义了任务，谁就定义了比较的坐标系。

| 项目 | 作者/归属 | 核心思路 | 靠什么长大 |
|---|---|---|---|
| **robosuite** | 斯坦福 SVL（学术实验室） | **薄薄一层**裹在 MuJoCo 上，只提供标准操作任务 + 机器人模型 | 任务定义被大量论文采用 |
| **ManiSkill** | 加州大学圣地亚哥分校 / Hillbot | 任务 benchmark + 排行榜 | 排行榜 + 基线数据 |
| **Isaac Lab** | NVIDIA | 万级并行 RL 环境；**任务/环境即产品** | 算力绑定 + 生态 |
| **MuJoCo Playground** | Google DeepMind | 在 MJX/Warp 上做标准 RL 环境 | 上游自带分发 |

**给你的启示**：**这是与驭臂现状最贴近、也最可抄的一类。** robosuite 的作者没有写引擎、没有写界面，只定义了"任务长什么样"，结果被大量论文引用。
注意：**他们的资产是任务库，不是代码量。**

### 2.5 【新框架派】重新下注"仿真应该怎么组织"

| 项目 | 核心思路 | 教训 |
|---|---|---|
| **Genesis** | 一个框架统一多物理求解器 + 可微 + 极快 | 曾因性能宣称引发公开争议 —— **说明"重新下注"必须能被别人复现** |
| **Newton** | NVIDIA + DeepMind + Disney 联合，**放进 Linux Foundation** 做多厂商中立项目 | 单个公司背书不够时，用**中立基金会**换信任 |
| **Taichi** | 把仿真当**编程语言问题**（可微编程语言），而不是应用问题 | 换抽象层能开新赛道，但需要极强的技术叙事 |
| **Drake** | 把机器人系统建成 **Diagram of Systems**；"model-based design" | 强调**教学与可验证性**，产物是框架 + 课程，不是软件 |

**给你的启示**：这一类赢在**叙事**（一句话说清"为什么需要我"）。你现在缺的正是这句话。

**★ 但 Newton 有一条驭臂该直接抄的工程做法：把 viewer 做成可插拔后端，并把"自定义面板"做成一等公民。**

Newton 的文档列出 `ViewerGL / ViewerRTX / ViewerFile / ViewerUSD / ViewerRerun / ViewerViser / ViewerNull`，**全部藏在同一个接口后面**（`set_model` / `begin_frame` / `log_state` / `end_frame`）。关键在于它暴露了：

```python
register_ui_callback(my_ui, position="side" | "stats" | "free" | "panel")
```

即 **"挂自己的 ImGui 面板"是官方支持的公开接口**，而且 `ViewerNull` 专门给无头/CI 用。

**对照驭臂**：驭臂要的"8 个自研面板"在 Newton 里是**一行注册**，在 MuJoCo Studio 里却要**接管官方页签栏、按截屏校准像素**（§5.2）。
**这不是驭臂的问题，是宿主的选择。** 但它给出了一条明确的判断标准：

> **选底座时，"能不能挂自己的面板"应该和"能不能跑物理"同等重要。**
> MuJoCo 引擎层很强，但它**故意没做 UI 扩展点**（官方 UI 文档原话：*"Individual UI elements **do not allow customization**"*）——
> 驭臂为这个选择付了 55% 的提交量。

### 2.6 【接口新潮派】换交互介质，而不是换引擎

| 项目 | 核心思路 |
|---|---|
| **MuJoCo MCP**（社区） | 把仿真器能力暴露成 **LLM 可调用的工具**（MCP 协议），让大模型直接做仿真 |

**给你的启示**：这条对你是**低成本高辨识度**的机会 —— 你的算法库本来就是"一个文件 + 一个类"，天然适合被 LLM 生成和挂载。这是别人还没占住的位。

## 三、横切：做得久的项目，共同的六条

> 下面六条是从上一章各项目里抽出来的共性。**每条都对照驭臂现状给结论**（实测）。

| # | 共性原则 | 别人的做法 | 驭臂现状 | 判定 |
|---|---|---|---|---|
| 1 | **核心稳定，外围可换** | 引擎二十年只做加法；引擎层 GUI 由用户自选 | 引擎当依赖 ✅；官方 GUI 想换但换不动 | ⚠️ 一半 |
| 1b | **⚠️ 原厂会亲自下场做应用** | MuJoCo Studio = 引擎原厂重写自己的工作台（§2.1）；Gazebo/Webots 同理 | 驭臂正与这个原厂应用**竞争同一块地** | 🔴 **最大结构性风险** |

## 五、诊断：真正的缺口

> 判定分级：🔴 结构性（不改就走不远）／🟠 重要（影响成长）／🟢 轻微／✅ 反而领先。

### 5.1 🔴 缺口一：没有"任务（Task）"，所以永远只能演示

**症状（实测）**：算法库 6 个算法，全部是**关节空间或轨迹级**：

| 算法 | 类型 |
|---|---|
| 关节 PD 位置控制 | 关节空间伺服 |
| 参数辨识 | 系统辨识（工具，非任务） |
| 数据录制与回放 | 基础设施 |
| 末端两点运动（任务空间 PD） | 轨迹级 |
| 正弦摆动 | 演示级 |
| 我的控制律_模板 | 模板 |

**没有任何一个带这些字段**：

- ❌ **成功判据**（什么叫"这个任务成功了"）
- ❌ **预算**（多少时间/步数内要成功）
- ❌ **失败语义**（超时算失败？碰撞算失败？没抓到算失败？）
- ❌ **可重复的初始条件**（同一任务每次起始状态一致才能比较）

**为什么这是结构性的**：插件基类 `控制插件` 定义了 `名称/说明/可调参数/插件状态/模型兼容性/模型已切换` —— 是一个**"控制器"接口**，不是一个**"任务"接口**。
在这个接口下，你能造出无穷多个"让机械臂动起来"的算法，**但永远无法回答"哪个更好"**，因为"更好"需要判据。

**对照**：robosuite / ManiSkill / Isaac Lab 的**全部价值就在这一层**。它们不比你多写引擎，它们只是**定义了任务**。

**修法（工作量很小，因为架构已经准备好了）**：给 `控制插件` 加三个可选字段（`成功判据` / `预算` / `初始条件`），再加一个评估器把"跑一次任务"变成"返回成功/失败 + 指标"。
你已经有 `指标桥.py`、`录制`、`参数辨识` 的闭环链路 —— 缺的只是**把"判据"放进插件接口**。

### 5.2 🔴 缺口二：精力被"宿主框架"持续抽走，而不是长产品

**症状（git 实测，最近 22 次提交）**：

| 类别 | 提交数 | 占比 | 例子 |
|---|---|---|---|
| **界面细节返工** | **12** | **55%** | 页签校准 / 停止每帧抢焦点 / 配色改成官方页签色 / 窗口开关落盘 / 红框空白双根因 / 假页签按截屏校准 |
| 双语 i18n | 3 | 14% | 文案机制 / 全部面板翻译 / 语言按钮取证 |
| 文档与基建 | 5 | 23% | 设计规格 / gitignore / 验收证据回填 / 进度回填 |
| **产品能力** | **2** | **9%** | 默认静止 + 物理总闸 / 中文字体补丁 |

（分类口径：按提交标题关键词归类，不是按改动行数 —— 界面类提交往往动得少但改得频繁。
精确计数脚本见附录 A，可复核。）

`界面侧栏改造_设计规格.md` §10 更直白：**同一天（2026-10-06）返工四轮**，加上 §10.1–10.3 追加修复。

**读法**：55% 的提交在跟宿主框架的布局搏斗，**只有 9% 在长产品能力**。
这不是"不努力"——22 次提交说明很勤奋；是**精力的去向被架构决定了**。

**根因**：官方 Studio 的 ImGui 布局**没有给第三方留位置** —— 你只能"接管官方页签栏""伪装页签""按用户截屏校准像素位置（官方页签实际约 118px，不是公式算的 67px）"。
**这不是你写得差，是你在跟一个不打算被扩展的宿主搏斗。**

**对照**：MuJoCo 官方文档明说可视化器"让用户自选 GUI 库" —— 意思是**它从没打算让第三方改它的 GUI**。
所以"重建 19 个面板"这件事，我上一份报告估的是 5700~9000 行、2~4.5 人月；**git 历史现在给出了更贵的实测价：界面细节的边际成本高到 13/22 的精力占比。**

**修法**：把界面投入**冻结在维护档** —— 不再新增重建官方面板的工作，只保留"我方面板 + 菜单入口"的混合形态（这是你现在实际已经能用的形态）。省下来的精力投到 5.1。

**症状**：能被外人使用的东西 = 0。

**对照**：所有活得久的项目都有"别人能拿走的东西"：

| 项目 | 外人拿走的资产 |
|---|---|
| robosuite | 任务定义（被论文引用） |

你现在的反馈回路只有一条：用户（你自己）试用 → 报界面问题 → 修界面。这个回路**只能优化体验，不能指出方向**。

### 5.4 🟠 缺口四：Python 独占 11 139 行，性能与维护双紧

单进程 CPython 扛 1kHz 控制回路 + 界面 + 录制 + 辨识。实测量级：`mj_step` 6.33µs、完整控制回路 8.13µs（前份报告实测）。当前够用，但：

**对照**：主流做法是**热路径下沉**（引擎 C/C++/Warp，上层 Python）或者**换 GPU**（MJX / Warp / Isaac）。你的热路径已经在 C 引擎里了 ✅，这一条**不急**，但要**知道天花板在哪**。

## 六、你迷茫的真正原因

把上面拼起来，结论很干脆：

> **你把"工程成熟度"当成了目标，而工程成熟度不是方向，是一种状态。**
> 状态可以无限打磨（于是有了 13/22 次界面返工），但**只有方向能告诉你"够了"**。

具体机制（三条同时成立）：

1. **反馈回路单一**：只有"自己用 → 报界面问题 → 修"，所以所有精力自然流向界面
2. **没有判据**：没有任务就没有"成功"，于是没有"做完了"的时刻（5.1）
3. **没有出口**：没有外人用，就没有外部需求来牵引方向（5.3）

**这不是你一个人的问题。** 所有"先做工具、再想用途"的项目都会走到这一步。区别只在于：走得出去的项目，都在某个时刻**强行定义了"这个工具为谁解决什么"**（robosuite 定义任务、Taichi 定义语言、Newton 定义中立标准）。

## 七、能学什么、改什么（按优先级）

### 7.1 🔴 P0：把"任务"立成一等公民

**目标**：让 6 个演示 → 变成"可比较、可复现、可积累"的任务集。

**最小改法**（不推翻现有架构，只加字段）。★ **机制对齐官方 MJPC 的"残差"做法**（见 §2.1）：
**不发明判据体系，而是把"任务是否解决"表达成残差向量**——残差从已有的 `指标桥.py` 取。

```python
class 我的任务(控制插件):
    名称 = "末端到点"
    # ↓ 新增：任务语义（都可选；不写 = 现在的"纯控制器"模式，向后兼容）
    残差 = lambda self: {                       # 「任务解决时趋近 0」（MJPC 原话）
        "末端位置误差": self.到目标距离(),        # ← 来自 指标桥.py
        "关节速度":     self.最大关节速度(),
    }
    权重 = {"末端位置误差": 1.0, "关节速度": 0.01}   # 对齐 MJPC 的 wᵢ
    成功阈值 = {"末端位置误差": 0.005}              # 残差落到阈值内 = 成功
    预算     = {"最大步数": 2000, "最大秒": 4.0}     # 超预算 = 失败
    初始条件 = {"qpos": [...], "随机化": {"qpos": 0.02}}   # 可重复
```

再加一个 `评估器`：一次运行 → `(成功/失败, 代价曲线, 指标字典)`，写入 `输出/`。

**为什么照 MJPC 这个形状抄，而不是自己设计"成功判据"**：
- **同构**：驭臂已有 `指标桥` + 参数辨识的残差思想 + 录制时序数据，**不需要新建判据体系**；
- **可比**：任务一旦是"残差 × 权重 × 范数"，两个算法的**代价曲线可直接比大小** —— 这就是"能回答哪个更好"；
- **不引入新 DSL**：残差用 Python 表达式（或 MuJoCo 自定义 sensor）表达，**算法作者仍然只写 Python**，符合驭臂既有形态；
- **有官方先例背书**：这是 Google DeepMind 在"任务"这一层公开采用的做法，不是我们拍脑袋。

**为什么这一条压倒其他**：它同时解决 5.1（无判据）、5.3（无外部资产）、第六章（无方向）三件事。
**工作量估计**：插件接口加"残差/权重/阈值/预算"四个可选字段 + 评估器 + 2 个示范任务 ≈ **300~600 行**。相对 11 139 行存量这是很小的改动，但会改变这个软件的性质。

### 7.2 🔴 P0：把界面投入冻结在维护档

- **停止**"重建官方 19 个面板"这条线
- **保留**现在能用的形态：我方面板 + 菜单入口 + 官方面板共存
- **规则**：界面只接受"用户报了才修"，不再主动重做
- 省下的精力全部投 7.1

**依据（三条，按分量排序）**：
1. **主场劣势**：界面定制度是 **Studio 会追平的地方** —— 它 Future Work ② 原文就是"make use of the flexibility offered by Dear ImGui"。**它是原厂，改 `gui.cc` 比重建便宜得多。**
2. **投入产出实测**：12/22（55%）次提交是界面返工、仅 2/22（9%）是产品能力。
3. **宿主不配合**：官方宿主设计上就没给第三方 GUI 留位置（只能"接管页签栏""按截屏校准像素"）。

**换个说法**：你现在的界面优势是**真实的**（换肤、双语、侧栏、面板窗都做出来了），
但它建在**对手随时能推平的地基**上。**不要在这里加仓；守住已有的即可。**

### 7.3 🟠 P1：给工具一个出口（三选一）

| **A. 开放算法库格式** | 把 `算法库` 的插件接口写成公开规范 + 一个 `pip install` 得出去的最小包，别人能写算法挂到你的外壳 | 要写文档、要处理别人的环境差异 | 想让别人用你的工具 |

| **C. 走 LLM 接口** | 把算法库暴露成 LLM 可生成/可挂载的工具（MCP 之类） | 新赛道，不确定性高 | 想要辨识度、抢身位 |

**建议先 A 后 B**：A 的改动小（你的接口已经够干净），B 是长期资产。

### 7.4 🟠 P1：把中文能力从"本机技巧"变成"可分发能力"

上一份报告的阶段 1，仍未做：汉字源从 Apple 的 STHeiti 换成 **OFL 开源 CJK 字体**（约 50~150 行），并把字体探针接进 `--自检`。
**理由**：现在中文能显示依赖①本机补丁②上游一个未承诺的实现细节。**要给别人用，这两条都必须变成可验证的。**

### 7.5 🟢 P2：清理文档漂移（实测 12 个文件）

实测：**12 个文件**的注释仍在宣称"面板只能画 ASCII / 官方 UI 字体没有中文字形"，
而字体补丁**早已生效**（两个主字体各 3771 个汉字码位，`--状态` 输出 `★ 已打补丁`）、双语也**已经上线**。

| 位置 | 文件 |
|---|---|
| 面板（6） | `关于面板.py:37`、`参数面板.py:128`、`展示面板.py:34`、`辨识面板.py`、`算法面板.py`、`曲线基类.py` |
| 算法（6，均在 docstring 的 `英文名` 注释处） | `关节pd控制.py`、`参数辨识插件.py`、`我的控制律_模板.py`、`数据录制.py`、`末端两点运动.py`、`正弦摆动.py` |

典型原文（**现在已经是错的**）：

```python
# 软件/面板/参数面板.py:128
# ★ 面板上只画 ASCII：官方 UI 字体没有中文字形（画中文会变成 ?）。
```

**为什么值得修**：这类注释会**误导下一个读代码的人（包括将来的你）**，让人以为中文还不能用，从而继续绕开中文写界面。
最要紧的是它污染**新算法模板** —— 别人照 `我的控制律_模板.py` 写算法时，会以为必须填 `英文名`。

**顺带审一次**：`软件/界面文字.py`（202 行）在 `文案.py` 双语机制上线后是否还需要（疑似历史层）。

**修法**：把这 12 处替换为"面板已支持中文（字体补丁 + `文案.py`）"，再跑一次 `验证/语言自检.py` 确认无回归。**约 30 分钟。**
