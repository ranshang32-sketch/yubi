# 面板外观风格（换肤）—— 可行性审查与方案推荐

> **审查对象**：需求「修改驭臂的面板样式（按钮 / 界面边框等），并且能在几种风格之间切换」
> **审查日期**：2026-09-17 ｜ **审查方式**：读官方 `viewer_app`/`native_viewer`/`viewer_protocol` 源码 + 逐符号摸 `dear_imgui` 绑定 + **真机开窗实测**（探针脚本已存档）
> **结论**：**可行**，而且是"逐帧推入皮肤"这一条干净的路，**不用 fork 官方、不用改一个官方文件**。但有 **3 个硬约束**和 **4 个必须先讲清的坑**，其中 2 个（坑 ① 与坑 ③）已在本次审查中实测复现。

---

## 一、结论速览

| 问题 | 结论 | 依据（都是实测，不是推测） |
|---|---|---|
| 能不能改**颜色**（按钮/边框/标题栏/文字…）？ | ✅ 能 | 绑定暴露 58 个颜色项（`Col`），实测推入生效 |
| 能不能改**形状**（圆角/边框粗细/内边距/间距…）？ | ✅ 能 | 绑定暴露 33 个样式项（`StyleVar`），实测推入生效 |
| 能不能**一次性全局设置**（像 `StyleColorsDark()` 那样）？ | ❌ **不能** | `GetStyle()` 只暴露 3 个可写字段，且**没有** `SetStyleColor` / `SetStyleVar`（实测 A1~A4） |
| **我们自己的 6 个面板**能不能换肤？ | ✅ 能 | 见证面板实测：自研面板开始画时皮肤已生效 = **True** |
| **官方那 19 个面板**能不能一起换肤？ | ✅ 能，**但必须包一层 `ux.setup_theme`** | 官方每帧都重设主题（实测 141 次/140 帧）；包装后实测 官方面板画完皮肤仍生效 = **True** |
| 切换风格要**重启**吗？ | ❌ 不用，**下一帧就变** | 皮肤是逐帧推入的 |
| 有没有**性能**代价？ | ✅ 可忽略 | 实测每帧 11.9 µs 推入 + 1.7 µs 弹出 |
| 会不会**拖垮窗口**？ | ✅ 不会 | 推入/弹出完全配对时 ImGui 一条错都不报（实测 51 帧无错）；皮肤抛异常可降级回官方主题 |
| 能不能**换字体**（构成主义的大字/无衬线标题）？ | ❌ **不能** | 绑定里没有 `AddFontFromFileTTF` / `ImFontAtlas`；`IO.FontGlobalScale` 是**只读**的（实测 E1） |
| 能不能**画斜线/色块**（构成主义的对角线）？ | ❌ **不能** | 绑定里**没有** `GetWindowDrawList`（实测 B5）；只有纹理绕路（见 3.7） |
| 会不会影响 3D 视图与物理？ | ✅ 完全不影响 | 皮肤只在 ImGui 绘制阶段生效，不碰 model/data/ctrl |

**一句话**：**颜色、圆角、边框、内边距、曲线配色 —— 全部可控（5 套风格做得到）；字体和矢量装饰 —— 做不到（得靠配色/边框/密度来"演"出风格）。**

## 二、需求拆解

你提的其实是 4 件事，难度差别很大：

| # | 需求 | 难度 | 说明 |
|---|---|---|---|
| 1 | 改面板样式（按钮、边框…） | **中** | 机制上只有一个可行解：逐帧 `Push`/`Pop`（见第三节） |
| 2 | 在几种风格之间切换 | **低** | 皮肤是数据驱动的，加一套风格 = 加一个 JSON 键 |
| 3 | 切换入口 + 记住选择 | **低** | 与现成的【模型库】面板 / `输出/面板状态.json` 同一套做法 |
| 4 | 风格与官方主题**共存**不打架 | **中** | ★ 官方每帧重设主题，必须处理（见 3.3） |

## 三、技术可行性（逐项，附实测证据）

### 3.1 换肤机制：只有"逐帧推入"这一条路

实测（探针 A 段，`优化/验证/外观探针_输出.txt`）：

```
A1 GetStyle() 暴露的字段：['FramePadding', 'ItemSpacing', 'WindowPadding']
A3 改不了的字段：WindowRounding / FrameRounding / WindowBorderSize /
                FrameBorderSize / GrabRounding / ScrollbarSize（全部 AttributeError）
A4 全局改颜色/样式的函数：['SetColorEditOptions', 'TableSetBgColor']   ← 没有一个能用
```

也就是说：**没有"设置一次就永久生效"的入口**。可选的路只有两条：

| 路 | 可行性 | 结论 |
|---|---|---|
| ① 改 `GetStyle()` / 调 `SetStyleColor` | ❌ 绑定没暴露 | 死路 |
| ② 每帧 `PushStyleColor/PushStyleVar` → 画完 → `Pop` | ✅ 实测可用 | **采用** |

**为什么"推入"能覆盖整个窗口**：ImGui 的样式栈是**全局**的（不是 per-window）。
只要在**所有窗口 `Begin` 之前**推入、在**所有窗口 `End` 之后**弹出，
这一帧里画的每一个窗口（官方的 19 个 + 自研的 6 个）都会用这套皮肤。

实测证明它真的生效（探针 B1，用 `GetColorU32` 前后对比，不靠肉眼）：

```
B1 Col.Button：推入前=0xff544a47  推入后=0xff1f1fcc  弹出后=0xff544a47
   → ✓ 推入真的生效且可还原
B2 PushStyleVar（圆角/边框/内边距）推入+弹出：✓ 没有报错
B3 implot（曲线）可独立换肤：✓（implot.Col 16 项；★ 但 StyleVar 不能碰，见下方订正）
```

> 曲线面板走的是 **implot**，它有**自己的一套**栈，所以"曲线配色"要和主界面皮肤**分别**推入
> —— 这也是风格表里单列 `曲线` 一节的原因。
>
> ⚠️ **本节结论后来被实现阶段订正**：当时只试了 2 个 `implot.StyleVar`（恰好都安全）就写下"20 项可推入"。
> 实现时逐项实测发现 **20 项里有 9 项直接段错误**（枚举值与 .so 对不上 → 越界索引 → 野指针），
> 因此**曲线只换颜色、不碰 StyleVar**。详见 [第九节](#九实施结果方案-a-已落地2026-09-17) 与
> `优化/验证/implot样式项安全矩阵.txt`。

### 3.2 ★ 关键坑 ①：官方**每帧**都在重设主题，会把我们的皮肤抹掉

这是本次审查最重要的发现，也是"能不能给官方面板换肤"的分水岭。

官方 `viewer_app.py:298-301`：

```python
def build_gui(self) -> None:
    """Emit full Studio UI."""
    ux.setup_theme(self.theme)          # ★ 每帧都调！
    ux.configure_docking_layout(show_toolbar=self.show_toolbar)
```

而 `ux.setup_theme()` 是**直接改写全局样式**（不走 push 栈）。后果实测如下：

| 阶段 | 我们推入的皮肤 | 实测结果 |
|---|---|---|
| 自研面板绘制期（`USER=100`，早于官方 GUI） | 生效 | 见证 ①：**True**（实测按钮色 `0xff1f1fcc` = 皮肤色） |
| 官方 `build_gui()` 跑完（`INTERNAL=1`） | **被抹掉** | 见证 ②：**False**（读到的是官方主题色 `0xff544a47`） |

**解法（实测有效）**：把 `ux.setup_theme` 包一层 —— 官方设完主题，我们**立刻补推一次**：

```python
原版 = ux.setup_theme
def 包装(主题):
    原版(主题)
    if 本帧皮肤已推入:          # ★ 见坑 ③：必须加这个判断，否则首帧会不配对
        _推入皮肤色()
ux.setup_theme = 包装
```

包装之后的实测结果（探针 D 段 + 见证 ②③）：

```
D1 官方 ux.setup_theme 被调用 141 次 / 共 140 帧  → ★ 确认每帧都调
D2 皮肤补推时机：'官方setup_theme#11之后→补推'、'#12之后→补推'…
② 官方 GUI 画完之后皮肤仍生效：True
③ 弹出之前（官方 GUI 已画完）皮肤仍生效：True
```

> **代价与风险**：这是"劫持一个官方函数"，属于本项目一贯警惕的"未定义行为"。
> 缓解办法有两条，都不贵：
> ① 在 `骨架/官方接口清单.py` 里加一项自检：`ux.setup_theme` 存在、可调用、可替换；
> ② 包装函数内部 try/except，官方一改签名就打印中文警告并**自动退回"只换自研面板"模式**，绝不崩窗。

### 3.3 一帧内的时间线（★ 关键坑 ②：弹出必须排最后）

实测的派发顺序（探针 C5，每帧如此重复）：

```
UpdateEvent  ──► 皮肤推入（CRITICAL=1000，最高优先级）
BuildGuiEvent ──► ① 自研面板绘制（USER=100）
                  ② 官方 ViewerApp.build_gui（INTERNAL=1）→ 内部 setup_theme → 我们补推
                  ③ 皮肤弹出（priority=0）
viewer.sync() ──► 渲染并 EndFrame
```

**★ 关键坑 ②：弹出处理器必须用 `priority=0`，不能用 `INTERNAL`。**
官方文档对"同优先级"的顺序写的是「**undefined**」（`messages.py:229`），
而官方 `ViewerApp._on_build_gui` 正好也是 `INTERNAL=1`。
用 0（比 INTERNAL 更低）就能**永远排最后**，不依赖任何未定义行为 —— 本次探针就是这么做的，实测稳定。

### 3.4 ★ 关键坑 ③：跨帧不弹出，ImGui 会报错

实测（故意推入 1 个颜色 + 1 个变量且不弹）：

```
[00070] [imgui-error] (current settings: Assert=1, Log=1, Tooltip=1)
[00070] [imgui-error] In window 'Debug##Default': Missing PopStyleColor()
[00070] [imgui-error] In window 'Debug##Default': Missing PopStyleVar()
```

结论：**软件不会崩**（这版 ImGui 的错误只是"记录 + 悬浮提示"，不是 abort），
但会**刷错误日志**，而且 ImGui 会在帧末**把多余的那层丢掉**（实测：第 150 帧我们试图补弹时，报的是
`Calling PopStyleColor() too many times!` —— 说明栈里已经没有了）。

**所以皮肤必须是"每帧推、每帧弹"，不能"推一次永久生效"。**

### 3.5 ★ 关键坑 ④：万一某一帧中途抛异常，计数必须能自愈

如果某个面板在绘制中途抛异常，我们的"弹出"可能来不及执行。设计约定（写进皮肤桥）：

1. 每帧 `UpdateEvent` 开头：**无条件把本帧的推入计数清零**（不补弹 —— 因为 ImGui 已经丢掉了那层）；
2. 所有推入/弹出都包 try/except，失败只打印一行中文警告；
3. 皮肤初始化失败 → 整个皮肤功能自动关闭，界面回到官方主题（与面板出错隔离同一个思路）。

### 3.6 能覆盖到什么（逐元素）

| 界面元素 | 能不能换 | 靠哪个项 |
|---|---|---|
| 面板底色 / 子面板底 | ✅ | `WindowBg` / `ChildBg`（带 alpha 即半透明，见 3.7 末条） |
| **标题栏**（含激活/非激活/折叠） | ✅ | `TitleBg` / `TitleBgActive` / `TitleBgCollapsed` |
| **按钮**（常态/悬停/按下） | ✅ | `Button` / `ButtonHovered` / `ButtonActive` |
| 输入框 / 下拉框 / 滑杆槽 | ✅ | `FrameBg` / `FrameBgHovered` / `FrameBgActive` |
| 滑杆把手 / 勾选框 | ✅ | `SliderGrab` / `SliderGrabActive` / `CheckMark` |
| **边框**（窗口/子窗口/弹窗/控件） | ✅ | `WindowBorderSize` / `ChildBorderSize` / `PopupBorderSize` / `FrameBorderSize` + `Border` |
| **圆角**（窗口/控件/标签/滚动条/把手） | ✅ | `WindowRounding` / `FrameRounding` / `TabRounding` / `ScrollbarRounding` / `GrabRounding` |
| 表格（表头/隔行/边框） | ✅ | `TableHeaderBg` / `TableRowBg` / `TableRowBgAlt` / `TableBorder*` |
| 标签页（选中/悬停/暗淡 + 顶部色条） | ✅ | `Tab*` 系列（含 `TabSelectedOverline` —— 构成主义的"红线"就靠它） |
| 分隔线 / 分节标题 | ✅ | `Separator*` / `SeparatorTextBorderSize` / `SeparatorTextPadding` |
| 菜单栏 / 弹窗 / 模态遮罩 | ✅ | `MenuBarBg` / `PopupBg` / `ModalWindowDimBg` |
| **停靠分隔条**（官方布局的分栏线） | ✅ | `DockingSeparatorSize` + `DockingPreview` |
| 滚动条 | ✅ | `ScrollbarBg` + 3 态 + `ScrollbarSize` |
| **实时曲线**（监控/录制/辨识面板） | ✅ | `implot.Col` 16 项 + `implot.StyleVar` 20 项 + 8 色调色板 |
| 文本层级（正文/次要/链接/选中背景） | ✅ | `Text` / `TextDisabled` / `TextLink` / `TextSelectedBg` |
| **字体 / 字号** | ❌ | 见 3.7 |
| 3D 视图里的机械臂、地面、网格 | ❌（也不该动） | 那是 MuJoCo 渲染，与 ImGui 无关 |

### 3.7 做不到的三件事（以及各自的绕路）

| 做不到 | 硬证据 | 影响 | 绕路（成本） |
|---|---|---|---|
| **换字体** | 无 `AddFontFromFileTTF`/`ImFontAtlas`；`IO.FontGlobalScale` 只读（E1） | 构成主义那种"粗黑几何标题字"做不出来；只能用**内置字体** | ① 接受（推荐）：用配色/粗细边框/间距去表达风格；② 把标题用 Pillow 烘焙成**纹理**再用 `imgui.Image` 贴上去（`viewer.upload_image` 已存在、离线依赖里有 Pillow）—— 但**只对自研的 6 个面板有效**，官方 19 个面板仍做不到，约 +1~2 天 |
| **画斜线/多边形/色块** | 无 `GetWindowDrawList`（B5） | 构成主义的对角线构图做不出来 | 同上（纹理绕路）；或改用"红/黑**色块 + 粗边框**"的近似表达（推荐，零成本） |
| **单独的标题文字色** | ImGui 的窗口标题用 `ImGuiCol.Text`，没有独立的"标题文字色" | 「黑底白字标题 + 白底黑字正文」这种经典对比**做不到** | 让标题栏用**中间明度**的底色（如正红 `#E03A2F` + 近黑文字），或让正文与标题共用同一文字色 —— 5 套风格都是按这个约束配的 |

> ★ 上表中第 3 条是从 ImGui 渲染模型推出的（标题绘制用 `ImGuiCol.Text`），
> **建议实现第一版时目视确认一次**；若真机效果不佳，只需调整该风格 `TitleBg` 的明度，不影响方案。

**还有一个待目视确认项：半透明**。`现代深色(#1B1D23E8)` 与 `航天测控(#0A0F14F0)` 都用了带 α 的底色，
机制上 ImGui 会把 `WindowBg` 的 α 与全局 `Alpha` 相乘后交给渲染器混合（即"面板半透明、能透出后面的 3D 视图"）。
这一点**本次没做像素级验证**（需要截图比对）。若不成立，把那两个色的 α 改成 `FF`（不透明）即可，
风格表里只有 2 个值需要动，不影响其余参数。

**为什么是这 5 套**：
- 你点名的 3 套（极简 / 构成主义 / 共产主义）全部保留，并按 ImGui 的真实能力重新配过色（不是照搬脑补）；
- 补的第 4 套是**实用默认**（现代深色）—— 因为风格切换功能必须有一个"平时就开着不难受"的选项，否则大家最终都会切回官方；
- 补的第 5 套（航天测控）覆盖**另一个极端**：信息密度最高、暗色、高对比 —— 它是"看曲线/调参数"时真正有用的那套；
- 5 套之间在**底色明度、圆角、边框粗细、密度**四个维度上都拉开了距离，切起来"一眼就看得出换了"。

## 五、三个实现方案

### 方案 A：完整皮肤（推荐）

```
软件/外观/风格表.json            5 套风格的纯数据（= 优化/风格表.json 搬进软件/）
软件/外观/皮肤桥.py              viewer 侧插件：
                                  · UpdateEvent(CRITICAL) → 推入本帧皮肤
                                  · 包装 ux.setup_theme() → 官方面板也跟着变
                                  · BuildGuiEvent(priority=0) → 弹出 + 容错自愈

```

- **改动范围**：新增 3 个文件 + 现有 3 个文件各加十几行；**一个官方文件都不改**；面板仍是"丢进 `面板/` 就自动加载"的老约定。
- **优点**：官方 19 个 + 自研 6 个面板**一起**换肤，界面统一；数据驱动，加风格 = 加一个键；随时可关（`风格=关` 完全回到官方外观）。
- **缺点**：依赖"包装 `ux.setup_theme`"这一个未定义行为（有自检 + 自动降级兜底）。

### 方案 B：只换自研面板（零劫持）

不做 `setup_theme` 包装，只保留"逐帧推入"。

- **优点**：完全不碰官方函数，风险最低；实现量约为 A 的 40%。
- **缺点**：**官方的 19 个面板（Controls / Simulation / Joints / Rendering…）保持官方配色**，界面会同时存在两套皮肤 —— 观感上"半边脸"。**只建议作为 A 的降级路径**，不建议作为交付形态。

### 方案 C：只用官方主题（零成本，已实现）

就是现在的 `--主题 dark/light/classic`（3 种，官方内置）。

- **优点**：零成本、零风险、官方维护。
- **缺点**：只有 3 种，且**做不出**构成主义/共产主义这类风格 —— 它只能改"深/浅/经典"，不能改圆角、边框粗细、强调色。

### 9.5 实施后追加：第三个坑 —— 面板文字与字体（"弹窗里很多问号"）

用户实测反馈：面板（浮动小窗口）里出现很多 `?`。排查结论与处置：

| 项 | 结论 | 证据 |
|---|---|---|
| 是不是数据/编码坏了？ | ❌ 不是 | 终端输出、JSON、文档里的中文全部正常 |
| 真正原因 | 官方 Studio 的 UI 字体**只有** Atkinson Hyperlegible（纯拉丁，362 个码位）+ FontAwesome，**无任何中文字形**；ImGui 遇到图集里没有的字符会回退画 `ImFont::FallbackChar`（默认 `'?'`） | `优化/验证/字体覆盖_实测.txt`（fontTools 读 cmap 逐字符核对） |
| 能不能装个中文字体？ | ❌ 不能 | 绑定里**没有** `AddFontFromFileTTF`/`ImFontAtlas`，`IO` 上没有 `Fonts`，`FontGlobalScale` 只读；imgui 自己的提示就是"要 CJK 得在 C++ 里 `io.Fonts->AddFontFromFileTTF()`" |

### 9.6 风格集调整（评审后替换两套，2026-09-17）

**复盘：为什么那两套翻车**（不是配色调错，是方向错）：
