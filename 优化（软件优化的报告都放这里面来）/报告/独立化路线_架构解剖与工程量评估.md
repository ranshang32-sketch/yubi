## 〇、结论速览

### 0.1 三句话回答

| 问题 | 回答 | 一句话依据 |
|---|---|---|
| ① 是不是沿用 Studio 界面、基层没动？ | **对，而且"没动"的程度比您想的更彻底** —— 连"19 个面板"都不是 C++ 硬编码的，而是官方 **501 行 Python**（`viewer_app.py`）在运行时画出来的 | §2.2 源码取证 |
| ① 这**是不是**中文显示不了的根因？ | **不是。** 根因是**字体文件里没有汉字字形**，与界面程序是谁写的无关。而且**已经解决了**（面板能显示中文，1245 个汉字零缺字） | §3，实测 |
| ② 完全自主可行吗？工程量多大？ | **可行，但要先拆清楚"自主哪一层"。** 三档自主的工程量差 **20 倍以上**：**换界面外壳 0.57~0.90 万行 Python（2~4.5 人月，推荐）**；连 GUI 框架一起换 0.80~1.22 万行（贵约 40%，且丢 PBR 画质）；连物理引擎一起重写 **13 万行 C + 十年积累（不可行也不必要）** | §5、§6 |

### 0.2 最重要的一条：您手里已经有一个"鸿蒙"了

用户猜的"类似鸿蒙和安卓"，**方向上对，但层次说反了一点**，纠正如下：

| 类比对象 | 鸿蒙 / 安卓 | 本项目 / MuJoCo Studio |
|---|---|---|
| 内核（不可替换、十年积累） | Linux 内核 | **MuJoCo 物理引擎（13.0 万行 C）** |
| 运行时 | Android Runtime | MuJoCo C API / Python 绑定 |
| 应用框架（自主的第一层） | ArkUI / 方舟框架 | **Dear ImGui + ImPlot 组件（官方二进制提供）** |
| **系统应用 / 桌面（真正"长得像谁"的一层）** | HarmonyOS 桌面 | **Studio 的 19 个面板 + ViewerApp** |
| 我方应用 | — | **驭臂：8 个自研面板 + 算法库 + 项目机制** |

★ **关键事实**：**最底下那层"界面基层"，我们其实已经动过了，而且动得比别人以为的深。**
`软件/面板/` 下 **12 个文件、3005 行**是**我们自己写的 ImGui 面板**，它们和官方 19 个面板**没有任何代码继承关系**，只是共用了官方提供的绘图组件（`dear_imgui` / `implot`）。
换句话说：**我们现在跑的是"两个界面程序并排跑在同一个 ImGui 上下文里"** —— 官方的 19 个面板 + 我们的工作台。

所以问题不是"要不要从零开始造界面"，而是：
**"要不要把官方那 19 个面板也换成我们自己写的"** —— 这是一个**可选的、可增量做的事**，不是一道非黑即白的门槛。

## 一、先明确"完全属于自己的软件"到底指什么

"自主"不是一个开关，而是**五个可以分别拥有的层**。把层分清楚，工程量问题才可回答：

| 层 | 内容 | 谁拥有 | 本机体积 / 行数 |
|---|---|---|---|
| L1 物理引擎 | 接触动力学、约束求解、积分器、传感器 | 上游（Google DeepMind） | `libmujoco` 9.65 MB ／ 13.0 万行 C |
| L2 渲染与材质 | Filament PBR、22 个 `.filamat` 材质包、着色器 | 上游 + Google（Filament） | 约 9 MB 资产 ／ 编译进 .so |
| L3 界面组件 | Dear ImGui 1.92 / ImPlot / SDL2 窗口（来自官方二进制） | 上游打包，我方**免费用** | 4 个 .so 共 12.1 MB ／ 绑定层 5837 行 |
| L4 **应用外壳（19 个面板 + 窗口布局）** | `viewer_app.py` + 编译版 `ux` | 上游写，**但我方可以整体替换** | 501 + 624 行 Python ／ `ux.so` 1.41 MB |
| L5 **我方应用** | 工作台 8 面板 + 算法库 + 项目机制 + 桥接层 | **100% 我方** | **11 401 行 Python**（`软件/` 8202 + `算法库/` 1476 + `工具/` 1723） |

**判断**：L5 已经是 100% 自己的。**"完全自主"的真实含义只可能是"把 L4 也吃掉"，极端情况下再把 L3/L1 吃掉。**

这也是为什么本报告的工程量估算会给出**差 50 倍**的三档：因为"自主"这三个字在 L4/L3/L1 上的价格完全不同。

### 2.2 最反直觉的一条发现

**"19 个面板"不是 C++ 里写死的，而是 501 行 Python 在每帧拼装出来的。**

`viewer_app.py` 的 `build_gui()` 就是一个普通 Python 方法，逐行调用组件：

```python
def build_gui(self) -> None:
    ux.setup_theme(self.theme)
    ux.configure_docking_layout(show_toolbar=self.show_toolbar)
    if imgui.BeginMainMenuBar():            # ← 菜单栏是 Python 画的
        if imgui.BeginMenu('File'): ...     # ← 菜单项也是
    imgui.Begin('Options')                  # ← 左栏面板窗口
    ux.simulation_gui(...)                  # ← 内容来自编译版 ux
    if imgui.TreeNodeEx('Physics Settings', node_flags): ux.physics_gui(self.model)
    ...
    imgui.Begin('Inspector')                # ← 右栏面板窗口
    if imgui.TreeNodeEx('Controls', node_flags): ux.controls_gui(...)
    ...
```

且它**以插件身份注册**，不是硬接线：

```python
@messages.handler(priority=messages.Priority.CRITICAL)
def _on_viewer_init(self, event): ...          # 缓存 viewer 引用
@messages.handler(priority=messages.Priority.INTERNAL)
def _on_build_gui(self, _: messages.BuildGuiEvent) -> None:
    self.build_gui()                            # ← 「画整个界面」只是收到一个事件
```

**这意味着**：只要不注册 `ViewerApp`、换成自己的类，官方那 19 个面板就会**整体消失**，窗口里只剩我们自己的东西。**这不是 fork，是官方设计好的插件位。**

`native_viewer.NativeViewer(..., plugins=[...])` 的 `plugins` 参数就是那个插槽（`native_viewer.py` 第 30 行）。

### 2.3 所以我方现在到底"基层动没动"

- **动的部分（我方 100% 自主）**：`软件/面板/` 全部 12 个文件、`面板容器.py`（一个窗口 + 页签 + 顶部菜单 Panels）、`面板注册表.py`（F9 恢复 / 弹出收回 / 重置版面）、`皮肤桥.py`（逐帧推样式覆盖官方主题）、`界面文字.py`、算法库、项目机制。
- **没动的部分**：`ux.so` 里那 30 个面板函数（物理参数、渲染设置、关节、传感器、Watch、State、Profiler…）。**它们只以"官方附加面板"的身份存在，我方代码不对它们做任何修改**（唯一一处"改官方对象"是包装 `ux.setup_theme`，且有自检盯着，见 `骨架/官方接口清单.py` 第 24 项）。

★ **结论**：**"基层基本没动"这个判断，对官方那 19 个面板成立；对界面框架不成立。** 我方已经在同一套组件上另起了一套界面。用户想要的那个"鸿蒙"，其实已经有雏形了。

## 三、中文显示不了的根本原因（以及它已经解决了）

### 3.1 根因链（每一环都有源码/实测证据）

```
① 官方 Studio 往 ImGui 字体图集里只装 3 个字体，文件名写死在 C++ 里
     src/experimental/studio/ux/fonts.h:
       inline constexpr char kMainFontFile[] = "AtkinsonHyperlegibleNext[wght].ttf";
       inline constexpr char kIconFontFile[] = "fontawesome-webfont.ttf";
       inline constexpr char kMonoFontFile[] = "AtkinsonHyperlegibleMono-Regular.ttf";
                    ↓
② Atkinson Hyperlegible 是**纯拉丁字体**（362 个码位，一个汉字都没有）
                    ↓
③ 加载函数把「字形范围」参数传成 nullptr，不做 CJK 声明
     static ImFont* AddFontCopy(..., const ImWchar* glyph_ranges = nullptr)
     AddStudioFonts(): AddFontCopy(main_data, 16.0f);          // ← 没给范围
                    ↓
④ ImGui 遇到图集里没有的字符 → 回退画 ImFont::FallbackChar（默认 '?'）
                    ↓
⑤ 面板上任何中文 → 一串 ?????
```

**与"界面程序是谁写的"完全无关。** 就算我们把 `viewer_app.py` 换成自己写的，只要还用官方加载的那份字体，中文照样是问号。反过来，只要字体文件里有汉字，官方那 19 个面板**也能显示中文**。

### 3.2 为什么"Python 加字体"这条路确实不通（复核确认）

本机实测 `dear_imgui` 的 315 个公开成员中，与字体有关的**全部**是：

```
GetFontSize   GetFontTexUvWhitePixel   PopFont   SetWindowFontScale
```

**没有** `AddFontFromFileTTF`、**没有** `PushFont`、**没有** `ImFontAtlas`、**没有** `ImFont` 类型、`IO.FontGlobalScale` 只读。
—— 所以"在 Python 里再挂一个中文字体"是**真的做不到**，旧报告这一句没错。

### 3.3 但有一条不碰二进制的路，而且已经跑通

**关键洞察**：字体是**按文件名**从 `assets/` 目录加载的 → **换文件不需要改二进制**。

（补充一个官方没写进文档的入口：`mujoco.experimental.studio` 认一个环境变量 **`MUJOCO_STUDIO_ASSETS_DIR`** 用来改写 assets 目录，网页/无头那条路用的就是它。
**但它解决不了中文** —— 因为**文件名和字形范围都写死在 C++ 里**，换目录只是换个地方找那三个 `.ttf`。真正管用的是**把汉字并进那个文件本身**。）

官方用的是 **Dear ImGui 1.92 的动态字形系统**（用到哪个码位就现烘焙哪个），所以只要 `.ttf` 文件里有汉字字形，面板就能显示，**连 CJK 范围都不用声明**。

> ★ **一条必须写下来的反证**（否则很容易被"看起来更有道理"的静态分析带偏）：
> `fonts.cc` 里 `AddFontCopy(main_data, 16.0f)` 把**字形范围传成 `nullptr`**。**在 ImGui 1.90 及更早，这确实等于"只加载 Latin，中文死路一条"** —— 但 1.92 起规则变了。
> Dear ImGui 1.92.0 官方 changelog 原文：
>
> > "Because the user **doesn't need to provide glyph ranges any more**, it is possible that a glyph … may be erroneously fetched from the primary font."（`docs/CHANGELOG.txt`，1.92.0 · Font Merging 段）
> > "The value of `ImFontConfig::GlyphRanges[]` is **only useful for legacy backends**."（同文件）
> > "All `GetGlyphRangesXXXX()` functions are now **marked obsolete**."（同文件）
>
> 即：**在 1.92 里 `glyph_ranges = nullptr` 不是限制，而是新系统的正常用法**（官方自己的 `AddStudioFonts` 就是这么写的）。
> 所以判据只能是**运行时**：本机实测 `CalcTextSize('中') = 13.00 ≠ CalcTextSize('?') = 6.00` —— 汉字字形确实被烘进了图集。
> （本报告已用两种方法交叉验证这条结论：**上游源码规则** + **本机运行时数值**。）

已落地工具：`工具/打补丁_中文字体.py`（`--状态 / --建立 / --安装 / --还原`）

做法：用 fontTools 把 macOS 自带的 **STHeiti Light** 子集化后**合并进** Atkinson 字体（选 STHeiti 是因为它和 Atkinson **同为 glyf 轮廓、同为 unitsPerEm=1000**，不需要缩放；Hiragino/PingFang 是 CFF 轮廓，混 merge 会失败）。

**实测判定（数值，不靠肉眼）**：

| 指标 | 原始字体 | 补丁后 | 结论 |
|---|---|---|---|
| `CalcTextSize('中')` | 6.00（= `'?'` 的宽度） | **13.00** | 拿到真汉字字形 |
| 5 组拉丁样本宽度 | 242 / 158 / 257 / 361 / 23 | **逐位不变** | 拉丁观感没被改坏 |
| 字体内汉字码位 | **0** | **3771** | GB2312 一级字库全覆盖 |
| 字体字形总数 | 392 | 4223 | |

> ★★ **一个必须在团队内说清楚的坑：默认装完的官方包，面板是显示不了中文的。**
> 外面（包括 AI 助手）如果只去读 `site-packages` 里那个字体文件，会数出"4223 个字形、3771 个汉字"，
> 然后得出"**官方字体本来就带中文，开箱即用**"的结论 —— **这个结论是错的，而且后果是"新机器上中文不显示却不知道为什么"**。
>
> 证据（本报告实测，用仓库里的**官方原版备份** `工具/字体补丁/官方原字体/` 对比）：
>
> | | numGlyphs | cmap 码位 | 汉字 | 假名 | 谚文 | 西里尔 | 希腊 |
> |---|---|---|---|---|---|---|---|
> | **官方原版（备份）** | **392** | **362** | **0** | 0 | 0 | 0 | 4 |
> | 当前 site-packages（已打补丁） | 4223 | 4182 | 3771 | 0 | 0 | 0 | 4 |
>
> 官方原版的 `机 / 臂 / 中 / 文` **全部缺失** —— 它是一个 **392 字形的纯拉丁字体**（大小 114 KB）。
> 打补丁之后变成 1.7 MB / 4223 字形。**所以"中文能显示"完全是 `工具/打补丁_中文字体.py` 的功劳，不是官方的。**
>
> **推论（对换机器/重建环境很重要）**：`工具/重建环境.sh` 之后**必须重跑一次** `打补丁_中文字体.py`，
> 否则面板会静默退回一串 `?????`。这也正是 §6 阶段 1 要顺手把探针接进 `--自检` 的原因。
>
> **顺带一条边界**：补丁字体是**中文专用子集** —— 假名（あ/ア）、谚文（한）、西里尔（Д）、希腊（α）**全部没有**。
> 做中文没问题；**将来若要日文/韩文界面，需要改补丁脚本的字形来源**（因为字体是我们自己生成的，这是**配置问题**，不是像"官方不给字体 API"那样的硬限制）。
> 另附：官方网页路径（`headless_ui.cc`）**不显示中文**，原因见 §3.5 —— 与本机无关。
| **仓库全部文本用到的不同汉字** | — | **1245 个，缺 0 个** | 本报告新增实测 |

当前状态（`工具/打补丁_中文字体.py --状态`）：

```

AtkinsonHyperlegibleMono-Regular.ttf      3771  ★ 已打补丁（面板能显示中文）
fontawesome-webfont.ttf                      0  （不需补丁：图标字体）
```

**遗留问题（真正需要处理的一条）**：汉字源是 **Apple 随 macOS 附带的 STHeiti，许可只允许在 macOS 上使用**，所以合并产物**不能提交进仓库**（已在 `.gitignore`），也只能在 macOS 上分发。
→ 若要对外分发，需换成 **OFL 许可的开源 CJK 字体**（如 Noto Sans SC / 思源黑体 / 文泉驿）。**这是许可证问题，不是技术问题**，且脚本里已经找到过现成资产（`NotoSC-w400_lvl12.ttf`，见 `文档/驭臂_完整工作报告.md` §3.3）。

### 3.4 为什么"动态烘焙"这条路成立（机制已定位到源码行）

上面 §3.3 的结论依赖一个上游实现细节。本报告把它查到了**确切的源码行**，并**按 3.13.0 这个 tag 逐行核对**（与本机 wheel 版本一致）：

| 步 | 证据 | 位置 |
|---|---|---|
| ① | Studio 用的 ImGui 是 **1.92.6 WIP**，自报串可从二进制里直接读出 | `strings native_viewer_cc…so` |
| ② | **原生路径**显式打开新纹理后端标志：`io.BackendFlags \|= ImGuiBackendFlags_RendererHasTextures;` —— 而且**设在加载字体之前** | `src/experimental/studio/hal/window.cc:54`（@3.13.0） |
| ③ | ImGui 侧：只有**没**这个标志时才走"预加载全部字形范围"的旧分支 | `imgui_draw.cpp` v1.92.6 |
| ④ | 于是旧分支被跳过 → **字形按需烘焙**，`glyph_ranges = nullptr` 不再构成限制 | 同上 |
| ⑤ | 官方头文件原话：*"Since 1.92: specifying glyph ranges is only useful/necessary **if your backend doesn't support** `ImGuiBackendFlags_RendererHasTextures`!"* | `imgui.h` v1.92.6 |

**结论**：中文能显示**不是巧合，是官方原生路径主动选择了新机制**。这条链现在是从"上游源码"到"本机实测"完全闭合的。

### 3.5 一个顺带查出的上游不一致（值得知道，但不影响我们）

同一次核对发现：**官方两条渲染路径对字体的处理不一样。**

| 路径 | 是否打开 `RendererHasTextures` | 结果 |
|---|---|---|
| **原生窗口**（我们在用的） | ✅ `window.cc:54` 有 | 走新机制 → **中文能显示** |
| **网页/无头**（`launch_web`） | ❌ `headless_ui.cc` 只设了 `HasGamepad`，**没有这个标志** | 掉进旧分支 → **退回 Latin-1，中文不显示** |

`web/headless_ui.cc:89` 调的是**同一个** `AddStudioFonts`，所以差别纯粹来自那个标志位 —— **也就是说：同一个字体文件、同一个函数，原生能显示中文、网页不能。**这几乎肯定不是官方有意为之。

**对我们的意义**：**零。** 因为本项目走的是原生窗口；而且 3.13.0 的 wheel **根本没打包 `studio/web/dist/`**，`launch_web` 本来也起不来（控制台会打印 *"Could not find web viewer static files."*）。
记录在此只为两件事：① 说明"官方两条路径行为不一致"这个坑真实存在，将来若有人提"为什么网页版没中文"时有据可查；② 它是 §3.4 那个机制判断的**反向验证** —— 一个开标志、一个不开，结果就分岔了，正好证明起作用的就是那个标志。

### 3.6 顺带排除两条"看起来更彻底"的路

| 方案 | 为什么不做 |
|---|---|
| 改用官方经典 `simulate`（`src/render/classic`，5225 行） | ❌ **更差**。它用的是**编译进引擎的位图字体**：`mjrender.h` 里 `int charWidth[127]` / `charWidthBig[127]` —— **只覆盖 ASCII 0–126**。且 `mjr_changeFont()` 只是**重新缩放同一套位图**（`render_context.c` 里 `makeFont(con, fontscale)`），不是加载新字体。中文在经典 viewer 里是**物理上不可能**。 |
| 自己 fork 官方仓库、改 `fonts.cc` 加 CJK 范围后重编译 | ✅ **技术上完全可行**（源码 Apache-2.0，`build.sh` 齐备），但代价是**背上 Filament 的 C++ 构建链**（见 §5 路径 D），为了一个已经用换文件解决的问题不值得。 |

## 四、彻底不依赖 MuJoCo 的物理引擎？先看清价格

| 组件 | 行数（实测） | 说明 |
|---|---|---|
| `src/engine`（接触、约束、积分、被动力…） | **65 680** | 核心动力学 |
| `src/user`（用户 API、碰撞驱动、传感器、模型修改） | **33 581** | |
| `src/xml`（MJCF 解析器） | **10 199** | 建模语言 |
| `src/render/classic`（OpenGL 渲染） | **9 788** | |
| `plugin`（引擎插件） | **7 033** | |

| 再往上还有 | ImGui ~1.1 万行、ImPlot ~0.5 万行、**Filament（渲染引擎，数十万行 + 22 个材质包）** | |

**判断**：**重写物理引擎这一项不可行，且没必要。**
MuJoCo 的接触模型（soft/friction cone、椭圆摩擦锥）、隐式积分、`mjSOL_*` 求解器、传感器与执行器模型，是 **Google DeepMind 十余年、几十人年**的积累。自己写一个能跑机械臂 PID 的简易引擎不难（几百行 RK4 就够），但**一碰接触、摩擦、抓取就立刻失真**——而"参数辨识 + sim2real"正是本项目的技术主线（已有 1.47% 辨识误差的实测成绩），引擎一换，这条主线全部作废。

**这也是鸿蒙类比在此处失效的地方**：鸿蒙必须换掉 Linux 内核是因为**地缘政治与授权**；本项目拿的是 **Apache-2.0**，法律上**已经允许改、闭源、商用、收费**（唯一的红线是**不能叫 MuJoCo 名字**、要写"与 Google DeepMind 无关联"）。**没有"被迫自主"的外部压力，自主就纯粹是一道"你愿意花多少钱"的工程题。**

## 五、五条路线的工程量估算

> 估算方法（可复核）：以**本项目已实测的产能**为基准校准，不用行业空泛数字。
> 校准锚点：我方现有 L5 共 **11 401 行 Python**（`软件/` 8202 + `算法库/` 1476 + `工具/` 1723），
> 其中**界面相关 4 117 行**（`软件/面板/` 3005 + `皮肤桥.py` + `界面文字.py`），承担了 **8 个面板、40 个控件、10 处图表调用**。
> 官方参照：`ux/gui.cc` **2382 行** → 30 个面板函数；`ux/imgui_widgets.cc/.h` **1465 行** → 控件封装层。

### 路径 A：维持现状（继续加深外壳）

**做什么**：不动 L4，继续在 L5 上加算法、加面板、加实验。中文已解决。

| 项 | 估算 |
|---|---|
| 新增工程量 | **0**（这就是当前路线） |
| 持续成本 | **每次官方发版 3~10 人日**（本机 `mujoco` 平均 **26.5 天**发一版，最近 3 版间隔 23/20/13 天）→ 复核 24 项接口自检、重打字体补丁、跑验收脚本 |
| 自主程度 | L5 完全自主；L4 依赖上游 |
| 风险 | 官方把 `experimental.studio` 改名/重构 → 接口自检会先报警，但仍需跟着改 |

**评价**：✅ **性价比最高。** 除非有明确的外部诉求（对外分发、品牌、深度定制布局），这条路本身没有致命缺陷。

### 路径 B：保留 ImGui 组件，把"外壳"换成自己的（推荐的"真自主"）

**做什么**：不注册官方 `ViewerApp`，自己写一个 viewer 插件：自己的菜单栏、自己的面板布局、自己的全部面板内容。**继续用 L1/L2/L3（引擎 + 渲染 + ImGui 组件），彻底替换 L4。**

| 工作包 | 新增行数（估） | 说明 |
|---|---|---|
| B1 自己的 ViewerApp 骨架 | 500 ~ 800 | 菜单栏 / 停靠布局 / 状态栏 / 主题与存档。参照官方 `viewer_app.py`（501 行，Apache-2.0，可直接读着写） |
| B2 重建 19 个官方面板 | **3 000 ~ 4 500** | **主要成本，且是路径 B/C 共同的那块**。参照：官方 `ux/gui.cc` 2382 行 + `ux.cc` 绑定 584 行 ≈ 3 000 行 C++ 对应这 30 个函数；用 Python 重写 + 中文化，按 1.0~1.5 倍估 |
| B3 交互层（相机 / 拖动 / 拾取 / 快捷键） | 400 ~ 700 | ★ 比初稿大幅下调。**3D 视口本身不用重写**（`native_viewer_cc.Present` 继续用），要重写的只是"事件怎么接"——官方 `viewer_app_events.py` 才 624 行，而 `CameraMotion`/`Pick`/`InitPerturb`/`MovePerturb` 这些**能力函数仍在 `ux` 里可直接调** |
| B4 迁移我方现有 8 面板 | 600 ~ 1 000 | 大部分是**搬运 + 中文改写**（`界面文字.py` 的英文转换层可以退役） |
| B5 测试/打包/文档 | 1 200 ~ 2 000 | 相当于再造一遍 `优化/验证/` 那套探针 |
| **合计** | **≈ 5 700 ~ 9 000 行** | |

> ★ **本节相对初稿的修正（必须说明）**：初稿把 B3 估成 1 500~2 500 行，那是把"3D 视口"当成了要新写的东西 —— **错了**。
> 路径 B 的整个要点就是**保留 `native_viewer_cc` 这个窗口+渲染后端**，所以视口是白拿的。修正后路径 B 的工程量**下调约三分之一**，而路径 C 反而因为"视口要重写"相对更贵（见下）。
>
> **成本曲线（社区实测的参照物，本报告新增证据）**：
>
> | 做到什么程度 | 参照物 | 代码量 |
> |---|---|---|
> | 嵌入式视口 + 相机轨道/平移/缩放，**别的什么都没有** | `mujoco_qt` gist（PySide6 + PyOpenGL） | **约 160 行**（实测计数） |
> | ＋覆盖层 HUD、3 个 2D 曲线图、鼠标扰动 | `mujoco-python-viewer` | **479 行**核心 / 约 850 行整包（实测计数） |
> | ＋Qt 面板、带标签滑杆、设置对话框、profiler | `QMuJoCoSim`（C++20/Qt6） | **约 2 400 行 C++** |
> | 官方 `simulate` 参考 GUI 的完整功能面 | `simulate/`（GLFW + `mjr_render`） | **约 5 400 行 C++**（`simulate.cc` 一个文件就 3 400 行） |
>
> **结论**：**没有"200 行做出面板+滑杆+曲线"这种好事。** 视口便宜（约 160 行），**成本和风险全部集中在"面板 + 图表 + 交互细节"上** —— 这也正是本报告把 B2/C3 当作成本主体、而把 B3/C2 大幅下调的依据。

**工期换算**：按本项目已交付的 L5（11 401 行，含算法与工具）推算，**约 2 ~ 4.5 人月**（单人熟练开发者）；
若只做 **B1 + B3 + B4 的"最小可用自主界面"**（丢掉官方 19 面板，只保留自己的 8 个面板 + 3D 视口 + 控制滑杆），则约 **1 500 ~ 2 500 行 / 0.8 ~ 1.5 人月**。

**收益**：
- 界面**完全自主**：想怎么排就怎么排，**中文原生**（不再需要 `界面文字.py` 的 ASCII 兜底）
- 摆脱 `ux.so` 那 **30 个 `*_gui` 面板函数 + `setup_theme` + `reset_config`** → 不必再跟着官方改面板函数签名
  （★ 诚实修正：**24 项接口清单只会少 3 条**（`ux.*` 三条），不会"降到 10 项"。因为那 24 项里 8 条是 `messages`、其余是 launcher / handle / protocol —— **这些不管走哪条路都躲不掉**。
  所以路径 B 的真实收益是**摆脱最不稳定、最常变的那部分 API 语义**，而不是把接口数量砍掉一半。）
- 官方发版风险大幅下降（不再依赖 `ux` 的 GUI 函数行为）
- 顺带拿到一个能力：官方已把 `DockBuilder*` 全套停靠 API 暴露给 Python（`native_viewer_cc.RenderToTexture` / `UploadImage` 也在），所以**自研外壳能做出比官方更自由的布局**

**代价**：
- **失去**：Spec Explorer / Spec Editor（图形化改模型结构）、Profiler、SimHistory 时间线回放的**界面**
  （注意：`sim.so` 是独立模块，**回放能力本身还在**，只是没有官方那套 UI）
- 官方后续给 Studio 加的新面板，**不会**自动出现在你的软件里
- 需要自己维护主题、DPI、停靠布局存档

### 路径 C：连 ImGui / Filament 一起换掉（自研 GUI 栈）

**做什么**：换成 PySide6/Qt 或 Dear PyGui 等**自带完整控件 + CJK 字体支持**的 GUI 框架；
3D 视口改用 MuJoCo 的**经典 OpenGL 渲染**（`mjr_render`）直接画进框架的 GL 画布。

> ★ 一个必须纠正的直觉：**这不是"换个界面库"，而是把整条图形栈换掉。**
> 官方现在是 **SDL2 窗口 + Dear ImGui/ImPlot + Filament（macOS 上走 Metal）**；
> 路径 C 会变成 **Qt 窗口 + Qt 控件 + 经典 OpenGL 渲染器**。
> 换掉的不只是控件，**还有 PBR 画质和 22 个 `.filamat` 材质资产**。

| 工作包 | 新增行数（估） | 依据 |
|---|---|---|
| C1 GUI 骨架 + 主窗口 + 停靠布局 | 800 ~ 1 200 | Qt `QMainWindow` + `QDockWidget` 是现成的，比 ImGui 手搓省 |
| C2 3D 视口（**直接 GL 渲染**，非离屏取像素） | **300 ~ 700** | ★ **本报告最重要的乐观修正**：社区已有一个经过验证的 **约 145 行**范例（`mujoco_qt` gist，`QOpenGLWindow` + `mjv_updateScene` + `mjr_render` 直接画进 Qt 的 GL 上下文，相机轨道/平移/缩放约 30 行，无离屏、无回读、无翻转）。**视口本身是"一个周末"的量级，不是一个季度。** |
| C3 全部面板（我方 8 个 + 官方常用 10~19 个） | 4 000 ~ 6 000 | 与路径 B2/B4 同量 —— **面板工作量和"用哪个框架"几乎无关**，这才是真正的成本主体 |
| C4 曲线/图表（ImPlot 换成 pyqtgraph 等） | 500 ~ 1 000 | pyqtgraph 为实时曲线而设计，比 ImPlot 省事 |
| C5 物理↔界面线程桥重写 | 800 ~ 1 500 | 现在的桥是按 ImGui 消息事件写的，要重写成 Qt 信号槽 + `QThread` |
| C6 打包（.app / 三平台）与验收 | 1 800 ~ 2 800 | 含 `QSurfaceFormat` 兼容性配置（**配错就是全黑视口**，见下） |
| **合计** | **≈ 8 000 ~ 12 200 行** | **比路径 B（5 700~9 000）贵约 40%** |

**评价**：⚠️ **比路径 B 明显更贵，而收益并不更大。** 四条必须知道的坑：

1. **`launch_passive` 嵌入这条路在 macOS 上不可行**。官方文档明说：*"On MacOS, `launch_passive` requires that the user script is executed via a special `mjpython` launcher, this is needed to circumvent a platform limitation which requires **the main thread to be one that does the rendering**."* Qt 也要求事件循环在主线程 → **两边抢主线程**。
   而且 `viewer.Handle` **没有暴露任何原生窗口句柄**（只有 `cam / opt / pert / user_scn / set_figures / set_texts / ...`，没有 NSWindow/GLFW 指针），**没有受支持的 reparent 办法**。
   官方 issue **#1378**「How to embed the viewer into a QT window?」**从未被维护者解决**，提问者最后留言仍是 *"Sadly, no. I am still actively looking for solutions. My program currently uses 2 windows."*
   → **正确做法是像那份 gist 一样，自己用 `MjrContext` + `mjr_render` 重建视口**，而不是嵌入官方 viewer。
2. **丢掉 Filament PBR 观感**（见上方纠正框）。想要回来的话就得回到路径 B。
3. **需要 `mjr_` 渲染的一串环境前提**：GL 上下文**有线程亲和性**（"can only be made current on one thread at any given time，且后续所有渲染调用必须在同一线程"）；macOS 上 `MUJOCO_GL` **只接受 `cgl` 或 `glfw`**；必须给 **compatibility profile + depth + stencil** 的 `QSurfaceFormat`。
4. **不要走"离屏渲染 → 读回 → 喂图片控件"那条更慢的路**（很多人第一反应是这条）：
   - `mjr_renderToTexture` **在 C API 里根本不存在**（完整的 `mjr_*` 只有 28 个函数）；
   - `mujoco.Renderer` 的离屏尺寸**受 `model.vis.global_.offwidth/offheight` 限制，默认只有 640×480**，超了会**直接抛错**，必须去改 MJCF；
   - `Renderer.render()` 对 EGL/OSMesa/GLFW 调了 `np.flipud`，**对 Filament 不调** → 行序随后端变；
   - 每帧多一次 GPU→CPU→GPU 往返。

**许可提醒（跨平台时才会碰到）**：若真要上 Qt，**选 PySide6（LGPL-3.0）不要选 PyQt6（PyPI 上是 GPL-3.0-only）**；后者会让你的软件变成 GPL，除非买商业授权。另外 **Qt Quick 3D 是 GPLv3-or-商业，不是 LGPL**，别用它做 3D 视口 —— 用 `QOpenGLWidget`/`QOpenGLWindow` 没有这个问题。

**唯一值得走这条路的情形**：需要**跨平台**（Windows/Linux）、需要**嵌入到别人的系统**、或者需要**中文输入法**（Qt 原生支持 IME；ImGui 路线要自己接 SDL2 的 text input）。若确定只做 macOS 桌面工具，**不建议**。

### 路径 D：fork 官方仓库，改 C++ 后自己出 wheel

**做什么**：克隆 `google-deepmind/mujoco`，改 `src/experimental/studio/**`（例如彻底改换字体加载、增删面板、改 UI 布局），自己编译整个 pip 包。

| 项 | 实测 |
|---|---|
| 官方 Studio C++ 源码 | **14 037 行**（52 个文件，`src/experimental/studio/`） |
| Python 绑定层（pybind11） | **5 837 行** |
| 必须一起编译的第三方 | **Filament rc/1.76.0**（`cmake/third_party_deps/filament.cmake` 锁定 commit，构建时 `FetchContent`）、Dear ImGui、ImPlot、SDL2、Abseil、Eigen、qhull、libwebp、zlib… |
| 构建配置 | `src/experimental/studio/build.sh` 已就绪（`-DMUJOCO_USE_FILAMENT=ON -DMUJOCO_BUILD_STUDIO=ON`） |
| **主要成本** | **不是写代码，是维护构建链**：首次构建须编译 Filament（含 `matc`/`resgen`/`cmgen` 主机工具）+ 整个 MuJoCo 引擎，**数小时级**；每次跟随官方升级都要重做一遍并解合并冲突（官方 3.14.0 已发布，本机还是 3.13.0） |

**评价**：⚠️ **只在一件事上值得**：当你要改的东西**只有 C++ 能改**，且**改完必须随包分发**。
本项目当前**没有这样的需求**（中文已经用换字体文件解决；面板已经用 Python 解决）。

**如果将来真要走**，建议的**最小 fork**只有一处：`ux/fonts.cc` 的 `AddStudioFonts()` —— 加一个 CJK 字体加载 + 显式字形范围。**改 1 个文件、加约 40 行 C++**，就得到"官方那 19 个面板也能显示中文"，且不用维护合并了一千多个汉字的字体文件。这是 fork 路线的**唯一甜点**。

### 路径 E：完全自研（含物理引擎）

|---|---|
| 13.0 万行 C 引擎 + XML 解析器 + 渲染器 | **数十人年**，且需要动力学/数值方法博士级团队 |

## 六、推荐路线：分阶段"渐进自主"

不建议一次性切换，而是**在不停止日常使用的前提下逐块替换**。每一阶段都有明确的**进入条件**和**止损点**。

### 阶段 0（已完成）：外壳层自主

- 状态：✅ 已交付。工作台 8 面板、算法库、项目机制、换肤、录制、辨识、中文面板
- 自主层：L5 100%
- 官方依赖：24 项（有自检盯着）

### 阶段 1：把"中文"从补丁变成正式资产（**建议立刻做**）

**目标**：消除"字体补丁只能在 macOS 用、且源字体不可再分发"这个隐患。

- 动作：把 `工具/打补丁_中文字体.py` 的汉字源从 **STHeiti** 换成 **OFL 许可的开源 CJK 字体**（Noto Sans SC / 思源黑体，已确认仓库里曾有现成子集）
- 新增工程量：**约 50 ~ 150 行**（换字体源 + 处理 upem 缩放 + 验收）
- 进入条件：无，随时可做
- 收益：字体补丁**可随包分发、可跨平台**，中文从"本机技巧"变成"产品能力"

> ★ **必须同时立一条"回归项"，否则这条能力是悬空的**：
> 整个中文方案**依赖上游一个实现细节** —— "ImGui 1.92 会按需烘焙字形"。
> 这个前提**今天是成立的**（§3.3 的两条证据），但它**没有任何官方承诺**（Studio 本身在 `experimental.` 命名空间下，且从未进 changelog）。
> 万一将来官方换成静态图集、或显式传一个 Latin 字形范围，**面板会一夜之间全变回问号**。
> → 所以阶段 1 要顺手做一件事：**把 `优化（软件优化的报告都放这里面来）/验证/字体探针.py` 接进 `软件/主程序.py --自检`**，
> 让"中文还能不能显示"变成**每次启动/每次升级后都会自动回答的一个数（`CalcTextSize('中')` 是否 ≠ `CalcTextSize('?')`）**，而不是靠某天偶然发现界面花了。
> 这条正是本项目已有惯例的延续（`骨架/官方接口清单.py` 的 24 项自检、`零改动自检.py`、`校验项目.py`）—— **把"依赖上游的行为"变成可观测项，而不是信任项。**

### 阶段 2：把中文接进面板（**低成本、高观感收益**）

**目标**：让工作台 8 个面板显示中文，退役 `界面文字.py` 的英文转换层。

### 阶段 3：做"最小可用自主界面"（**决策点**）

## 八、回答最初的两个问题（最终口径）

### 8.1 "GUI 是不是还沿用的 MuJoCo Studio 的界面，基层基本没动？"

**是，也不是——必须分层说：**

- **窗口与 3D 渲染**：是，100% 官方（`native_viewer_cc.so`，只有 8 个方法，完全不画界面）
- **那 19 个现成面板的界面代码**：是，官方编译版（`ux.so`），我们没动过，也没法在 Python 里改
- **"19 个面板怎么摆"**：**不是**。那是 501 行**可读可改的 Python**（`viewer_app.py`），而且它是**以插件身份注册的**——不注册它，19 个面板就整体消失
- **我方的工作台（8 个面板）**：**完全不是**。3005 行自研 ImGui 代码，与官方 19 面板**零继承关系**，只是共用组件库

### 8.2 "界面无法显示中文的根本原因"是这个吗？

**不是。** 根因是**字体文件的字形覆盖**，与界面程序归属无关。而且它**已经解决了**：

- 本机状态：两个主字体各含 **3771 个汉字码位**，仓库全部文本用到的 **1245 个不同汉字零缺字**
- 判据（数值，非肉眼）：`CalcTextSize('中')` 由 `6.00`（回退字形）变为 `13.00`（真字形），5 组拉丁样本宽度逐位不变

### 8.3 "工程量多大，可行吗？"

| 自主到哪一层 | 工程量 | 工期（单人熟练） | 可行性 |
|---|---|---|---|
| L5 应用层（**现状**） | 已完成 11 401 行 | — | ✅ 已交付 |
| L4 界面外壳（**真正的"自己的软件"**） | 5 700 ~ 9 000 行 | 2 ~ 4.5 人月 | ✅ **可行，推荐** |
| 最小自主界面（阶段 3） | 1 500 ~ 2 500 行 | 0.8 ~ 1.5 人月 | ✅ **成本最低的验证点** |
| L3 图形组件自研（换 GUI 框架） | 8 000 ~ 12 200 行 | 3 ~ 6 人月 | ⚠️ 可行但比 L4 贵约 40%、还要丢 PBR 画质，除非要跨平台 |
| L1 物理引擎自研 | 13.0 万行 C | 数十人年 | ❌ 不可行、不必要 |

> **关于"换成别的 GUI 框架"的三种备选，为什么都没改变上面的排序**（本报告已核查，详见附录 E）：
> · **Dear PyGui**：MIT、有 macOS arm64/cp310 轮子、CJK 自 2.3 起自动烘焙、ImPlot 现成、**但官方文档明说它的 3D 绘图 API *不是硬件加速*、且没有深度缓冲**，所以 3D 必须"离屏渲染→贴纹理"，而这条路**在 MuJoCo + DPG 上没有任何先例**（社区零案例）。可做，但要先做技术验证。
> · **viser / mjviser（网页栈）**：**最省代码**（11~120 行就能有滑杆+曲线+3D），CJK 天然正确 —— **但 `mjviser` 明确写着"没有鼠标交互：点选/拖动刚体需要上游 viser 支持"**，而"拖动机械臂"正是本项目的核心交互之一 → **直接不满足需求**。
> · **纯 pyimgui + GLFW**：要手搓停靠窗口管理器、曲线库、渲染循环、文件对话框 —— 把 DPG/Qt 免费给的东西再造一遍。**不推荐。**
>
> **共同点（也是本报告最重要的结论之一）**：这三种替代**都改变不了"面板 + 图表 + 交互细节"这块主体成本**。
> 换框架换掉的是"视口怎么画"（本来就便宜，约 160 行），换不掉"面板要写多少"（本来就贵，数千行）。
> 所以**框架选型不是本项目的关键决策，"要不要重建那 19 个面板"才是。**

**关于鸿蒙类比的一句话总结**：
> 鸿蒙要换内核是因为**授权与地缘**，Android 不给它用；MuJoCo 给的是 **Apache-2.0**，法律上**已经允许改、闭源、商用**。
> 所以本项目不需要"鸿蒙时刻"——**需要的是一次关于"界面这层愿不愿意自己养"的成本判断**。
> 而这个判断的答案，取决于一个更小的问题：**官方那 19 个面板，你到底用几个？**
> 用得少（≤5 个）→ 走阶段 3+4，一两个月就能把界面变成自己的；
> 用得多 → 维持在阶段 0~2，性价比最高。

## 附录 E · 换 GUI 框架的备选核查（支撑 §8.3 的排序）

> 结论先行：**这三种替代都改变不了主体成本，还各自引入新风险。**
> 记录在此，是为了说明"选 ImGui 还是选 Qt/DPG/网页"**不是本项目的关键决策**。

| 备选 | 许可 / 版本 | CJK | 3D 视口 | 停靠布局 | 曲线 | 致命短板 |
|---|---|---|---|---|---|---|
| **Dear PyGui** | MIT · 2.3.1 · 有 macOS arm64/cp310 轮子 | ✅ 自 2.3 起**自动烘焙字形**，`add_font_chars` 等已废弃 | ⚠️ 官方文档原文：*"The drawing API 3D operations are **not hardware accelerated**"*，**且无深度缓冲**（文档叫你用画家算法）→ 只能"离屏渲染 → 每帧贴纹理" | ✅ 有，但官方说*"docking 是实验性的，因为**你不能用程序设置停靠位置**"* → **没法交付一套固定的默认版面** | ✅ 内置 ImPlot 系 | **MuJoCo + DPG 零先例**；纹理上传格式在 macOS 上**只支持 float32 RGBA**；CJK **输入法**打字仍有 bug |

> **关于网页栈的一条关键判断（已核查）**：桌面端与网页端要分开看。
> · 官方 **Studio 自带网页查看器**（`launch_web`）**能**满足拖动，但**在 3.13.0 的 pip 包里是坏的**（缺 Emscripten 的 `studio/web/dist/`，控制台会打印 *"Could not find web viewer static files."*；上游 issue #3580 / PR #3611 仍未合并）→ **今天装不起来**。
> · **viser** 装得起来、也覆盖了 CJK / 停靠 / 曲线 / 3D 四项，**唯独缺拖动**。
> · 一个有意思的旁证：已有一个 Meta 的机器人项目（`facebookresearch/SPIDER`）把 `mujoco-viser` 作为一等查看器选项 —— 说明这条路在机器人圈是被接受的，只是**不适合"要用手拽机械臂"的场景**。
>
> **所以判据很干净**：**"拖动机械臂"是不可让步的需求 → 网页栈出局，路径 C（PySide6 + `QOpenGLWidget` + pyqtgraph）才是跨平台时的答案**；若拖动可让步，viser 是"最省代码且满足其余四项"的选择。
> 另外：**"状态流 vs 像素流"这个结论证据很足**（Studio 网页端、viser、mjviser、Drake 的 meshcat 四个独立实现都选了状态流），但**"具体延迟数字"业界没有公开基准** —— 那需要在本机做一次 loopback 实测，本报告不编造。
| **纯 pyimgui + GLFW** | MIT · 文档停在 1.1.0 | ⚠️ 有 `add_font_from_file_ttf(path, size, glyph_ranges)` + `refresh_font_texture()`，但需自己处理 HiDPI 缩放 | 要自己接 GL | ❌ 要手搓窗口管理器 | ❌ 无 | 只给你 ImGui 本身：**停靠管理、曲线、渲染循环、文件对话框都得自己写** = 把 DPG/Qt 免费给的东西再造一遍 |
| **PySide6 / Qt**（路径 C 正文） | **LGPL-3.0**（对比 PyQt6 = GPL-3.0-only） | ✅ Qt 自带字体回退 + `QFontDatabase.addApplicationFont()`；**且有原生输入法** | ~160 行可读范例；但**不能嵌官方 viewer**，必须自己 `mjr_render` | ✅ `QDockWidget` | ✅ pyqtgraph | 贵约 40%；丢 Filament PBR；`QSurfaceFormat` 配错 = 全黑视口；**Qt Quick 3D 是 GPLv3，别用** |

**几个被顺手排除的选项**（避免重复调研）：
- **Kivy**：无 3D 引擎；CJK 要**逐个控件**设 `font_name`（没有全局默认字体）；无机器人先例。
- **Godot**：**没有成熟的 MuJoCo 绑定**（真正的参考是箱庭 Hakoniwa，且文档只覆盖 Windows/WSL2）。
- **Unity**：官方在树内就有插件（`mujoco/unity/`，C#，原生 `mj_step`，**自带"鼠标弹簧"拖拽刚体**），但 macOS 要手动拷 dylib 并过 Gatekeeper 信任。
- **Isaac Sim / Isaac Lab**：许可其实是宽松的（Apache-2.0 / BSD-3-Clause），**但 macOS 完全不支持**（只要 Ubuntu 22.04 或 Windows 11 + ≥16 GB 显存的 NVIDIA 卡）→ **平台层面直接出局**。
- **Rerun**：定位是"日志/查询/查看"的数据层（官方自述 *"The data layer for physical AI"*，PyPI 标 Alpha），**不是交互式控制 GUI**；它的交互只作用于**自己的查看器界面**（蓝图拖拽、选中面板、相机），**没有任何"拖一个 gizmo 把值拿回 Python"的 API** → **接不了实时控制滑杆**；且现在连一方的 MuJoCo 示例都没有了。（另：Rerun 的中文显示**未查证**，不要想当然。）
- **Napari**：原型快，但 **0.8.0 起放弃 Python 3.10**（本机正是 3.10.21），得钉在 `napari==0.7.0`；无机器人先例。

**一个值得记住的反面参照**：连 **MuJoCo Playground**（DeepMind 自己的旗舰 MuJoCo 强化学习库）**都不做 GUI**，而是转给第三方网页可视化 `rscope`。
→ 说明"自建 GUI"在这个生态里**不是标配动作**，本项目的做法属于少数派；要走就得认清成本。
