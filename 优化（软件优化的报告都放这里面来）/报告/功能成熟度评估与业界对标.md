# 驭臂 · 功能成熟度评估与业界对标 —— 差距清单与优化建议

> **评估对象**：`驭臂`（自研机器人仿真桌面软件，Python + MuJoCo 3.13.0，运行于 Apple M5 / macOS 26.5）
> **评估日期**：2026-09-22
> **评估方式**：① **读自己的代码取证**（不凭印象：逐文件统计、逐特性 grep、逐面板数控件）
> ② **实测**（开窗跑，量吞吐与稳定性）③ **业界对标调研**（Gazebo / Isaac Sim / CoppeliaSim / Webots / MuJoCo 生态，附来源链接）
> **结论先行**：**"机械臂离线仿真 + 自己写控制算法"这条主线已经成熟可用；短板集中在"感知类仿真（相机/雷达/IMU）、执行器真实感（电机+减速器+摩擦）、以及批量并行（RL/大数据）"三大块** —— 这三块恰好是我们的路线（复用官方 C++ 窗口层 + Python 上层壳）**结构性不擅长**的部分。

## 一、结论速览

### 1.1 一句话结论

| 维度 | 成熟度 | 说明 |
|---|---|---|
| **机械臂动力学仿真** | ✅ **成熟** | MuJoCo 承接；5 台真实机械臂（UR5e/UR10e/Panda/iiwa14/xArm7）+ 夹爪，实测控制误差 0.000° |

| **参数辨识（sysid）** | ✅ **可用且已验证** | 造已知真值闭环验证，误差 1.47%；界面化采样→辨识→看改善 |
| **数据录制与回放** | ✅ **可用** | 按物理步长采样，回放精确复现；CSV + `.meta.json`（版本+模型指纹+插件清单） |
| **交互与可用性** | 🟡 **基本够用** | 单窗口页签工作台、5 套皮肤、模型热切换、拖拽换模型；但**界面不能显示中文**（字体图集无法从 Python 注入） |
| **感知类仿真** | ❌ **缺失** | 相机/深度/分割/LiDAR/IMU/力觉/触觉 —— **一个都没接**（MuJoCo 底层全支持，我们没暴露） |
| **执行器真实感** | 🟡 **官方有、我们没接** | 界面里只有「扭矩直给」；但 **MuJoCo 自带 `dcmotor`（含热/饱和/电流环）、`lugre` 摩擦、`gear` 减速比** —— 缺的是「暴露到界面」，不是「造轮子」 |
| **批量并行 / 强化学习** | ❌ **缺失** | 单环境单线程；没有 `mjx`/JAX、没有多环境、没有 Gym 接口 —— 训 RL 目前做不了 |
| **CAD / URDF 导入** | ❌ **缺失** | 模型库只认 `.xml/.mjb/.mjz`（33 个 XML、**0 个 URDF**）；CAD 要人工转换 |
| **运动规划** | ❌ **缺失** | 没有 MoveIt/规划器；只有演示级"雅可比转置 + 逆运动学"插件 |
| **精度与实时性** | ✅ **引擎很强，界面里钉在 1× 实时** | `mj_step` 实测 **2.87 µs/步 → 单线程 34.9 万步/秒 = 698× 实时**；但官方 `StepControl.set_speed()` 上限被钳在 100% → 界面里最快只能到实时（实测 0.86×，见第六节） |
| **可复现性** | ✅ **有意识、做得对** | 记录 `mujoco` 版本 + 模型指纹 + 插件清单；回放按物理步长对齐（实测曾因 100 Hz 录制导致偏差 297°，已修） |
| **合规** | ✅ **已闭环** | 名字不含 MuJoCo、关于页声明"与 Google DeepMind 无关联"、依赖 Apache-2.0/BSD 全覆盖 |

### 1.2 四个"必须先说清楚"的判断

1. **我们的强项是"薄壳 + 官方引擎"这条路线的强项**：物理精度、稳定性、渲染质量、19 个官方面板，全部白拿；我们自己写的 6869 行 Python 专注在"控制算法 + 辨识 + 录制 + 界面组织"。
2. **我们的短板分两种，必须分开看**：
   - **「官方 C++ 层没暴露给 Python 的」**（相机图像/深度/分割/触觉）→ 要**先做可行性探针**，不是纯 Python 能解决的；
   - **「官方早就有、只是我们没接的」**（**`dcmotor` 电机、`lugre` 摩擦、`gear` 减速比、URDF 导入、`mj_sensor` 读数**）→ **改配置 + 加界面就能拿到**，属于最划算的一类。
   把这两类混在一起排期，是我第一版的错误；本报告已按此分开（见第三、五节）。
3. **“性能”这件事要说准**：引擎本身极快（**698× 实时**），但界面里被官方 `StepControl` 钉在 **≤1× 实时**（实测 0.86×）。所以“能不能更快”**不是**改一行代码就能解决的 —— 第六节给了两组 A/B 实测和一个待查点，**不要据此盲目加速**。
4. **"我们缺的东西"里，有一半是全行业的空白**：调研（第四节）显示 —— **CAD(STEP/IGES) 导入、中文界面、图形化模型结构编辑器、传感器噪声的工程级真实感、"确定性+高性能"契约**，
   这五项在 **11 款受查软件的官方文档里都缺失或未查证**。
   所以本报告把缺口分成两类：**"别人有我们没有"（传感器、执行器真实感、URDF、批量并行）** 与 **"谁都没有"（上面五项）**。
   前者决定我们"能不能干活"，后者是我们可以主张差异化的地方 —— 两者的优先级完全不同，**不要混在一张清单里排期**。

### 2.5 可复现性（读 `plugins/数据录制.py` 取证）

`.meta.json` 记录三要素：`mujoco 版本 + python 版本`、`模型指纹`（`nq/nv/nu/nbody/ngeom` + 结构数值哈希 + 文件 sha256）、`插件清单`。
实测教训已固化在代码注释里：**录制频率必须对齐物理步长**（100 Hz 录 500 Hz 物理 → 回放偏差 297°）。

**业界数据格式对照（调研事实，供将来升级参考）**：

| 格式 | 谁在用 | 特点 |
|---|---|---|
| **CSV + JSON**（我们） | 我们 | 零依赖、Excel/pandas 直接看；**不适合大规模**（无索引、无压缩） |
| **HDF5** | robomimic、Isaac Lab (`HDF5DatasetFileHandler`) | **学习数据集事实标准**：单文件放多条 episode（`obs/actions/dones/states`） |
| **MCAP / rosbag2** | ROS 2 控制流（**自 ROS 2 Iron Irwini 起 mcap 成为 rosbag2 默认写入格式**） | 有公开规范（模块化容器、可索引、任意序列化）；**控制流日志的事实标准** |

**调研的两条补充澄清**（避免我们把标准名用错）：
- ROS 2 **没有**"规范性 bag 格式标准文档"（rosbag2 是插件架构），MCAP 本身才是那个有规范的东西；
- **ASAM OpenX 里的 OpenLABEL 是"标注"标准，不是日志格式** —— 别把它当数据格式对标项。

**建议（不急于改）**：现在 CSV 完全够用；
**等做批量仿真/RL 数据时再加 HDF5 导出**（按 robomimic 的 episode 结构），
**不要现在就换格式** —— 那会破坏已有录制文件的可读性与兼容性。
口径总结：**控制流走 MCAP、学习数据走 HDF5**，是当前最稳的组合。

## 三、能力缺口（按"对您实际工作的影响"排序）

> 每条给：**现状（取证）→ 业界怎么做 → 影响 → 补的成本量级**

### 3.1 传感器仿真：完全没有（影响：**大**）

**现状**：全代码 grep `camera / sensor / rangefinder / touch` → **0 个自研文件命中**；模型 XML 里也没有 `<sensor>`/`<camera>` 标签（只有 `default/motor/general/site/keyframe`）。
**业界（调研实测事实，附来源）**：
- **Gazebo（Jetty）**：相机 / 深度 / RGBD / **分割相机** / GPU Lidar / IMU / 力扭矩 / GPS / 接触 / 气压 / 磁力计 / 热成像…，**支持高斯噪声**与自定义更新率、相机畸变。
- **Webots（R2025a）**：噪声建模**最细** —— Camera 有 `noise` + `noiseMaskUrl`（自定义 PNG 噪声遮罩）；GPS 用 `accuracy` + `noiseCorrelation`（Gauss-Markov 漂移）；**`Recognition` 节点输出分割真值**（id / 相对位姿 / 尺寸 / 像素 bbox）。
  ⚠️ 但**并非人人都有 `noise` 字段**：Accelerometer/Gyro 只有 `resolution`，DistanceSensor/LightSensor **连 noise 都没有**；TouchSensor 的 force-3d **只有 3 轴力、没有力矩通道**。
- **CoppeliaSim**：强在**精确最小距离**（自定义检测体内，作用于 mesh/OC tree/点云）+ 深度缓冲，但**没有内建噪声模型、没有官方分割真值**。
- **MuJoCo 系（★★ 这条最容易踩错）**：传感器走 `mj_sensor*`，但
  **RGB/深度相机不在标准 sensor 模型里**（要程序化离屏渲染）；
  而且官方对 `sensor/noise` 的定义是"**不影响仿真**"——**它只是元数据标签，不会真的往读数里加噪声**，要加噪声得自己写。
  MuJoCo 也**没有 IMU 偏置/随机游走、没有扫描式 LiDAR、相机没有畸变/ISP**。
  → **这对我们是个机会**：官方把"传感器层"留白了，而 Python 上层壳恰好是最容易补这一层的地方。
  建议做法：**参数命名直接对齐 Gazebo/SDF 的 `noise.sdf`**（`mean/stddev` + `bias_mean/bias_stddev` + `dynamic_bias_stddev/correlation_time` + `precision` 量化），
  再叠加"时间戳/延迟/采样率/量化/相机畸变"—— 这样我们做出来的东西**术语不自定义、用户不用重新学**。
- **Genesis World**：**唯一把"传感器不完美"做成引擎级一等特性**的产品（IMU 含 noise/bias/random walk/轴间耦合/分辨率 + 全局 delay/jitter，并有 `read()` vs `read_ground_truth()` 双轨）。
- **Isaac Sim**：Camera/RayCaster/Contact/IMU/PVA/JointWrench + OVRTX 路径追踪视口 —— **但它在我们平台上跑不了**（见 4.2）。
**影响**：
- 做不了"视觉伺服 / 抓取 / 感知类算法"的验证；
- 做不了"带传感器噪声的鲁棒性实验"；
- 做不了"Sim2Real"的数据集生成。

**但这条要给出正确的"严重程度"（重要）**：三路调研的共同结论是 —— **"传感器噪声 + 延迟 + 采样率 + 量化 + 标定内参"的真实感，是全行业的普遍薄弱环节**：
11 款受查软件里，只有 **Genesis** 把它做成一等特性，**Webots** 在"噪声字段"上最完整但仍有传感器没有 noise 字段，
**MuJoCo / SAPIEN / Brax / ManiSkill** 都明显偏弱（ManiSkill 官方原话："At the moment there is only the Camera sensor type"）。
**所以这块"我们也缺"并不丢人，反而是清晰的差异化空档** —— 谁能把"不完美的传感器 + 可复现"做扎实，谁就有话说。
**补的成本**：**中等偏低**。MuJoCo 底层全支持（`mj_camera` / `mj_sensor*` / `mj_ray` 实测都在），缺的是"把图像从仿真拿到界面"这条路 —— 而 `native_viewer_cc` 里官方**已经有** `RenderToTexture` / `UploadImage`，所以原型量级是**天级**（不是周级）。

### 3.2 执行器真实感：只有"扭矩直给"（影响：**大**）—— 但★更正：MuJoCo 官方**已有**电机模型，我们只是没用

**现状**：模型里用的是 `<motor>`（`ur5e_torque.xml`：6 个 `motor` + 3 个 `general`），控制插件直接写 `ctrl[:] = τ`。
界面上没有任何"电机参数"可调。

**★ 这里我原先判断错了，调研把它纠正了（对方案影响很大）**：
**MuJoCo 从 3.7.0 起就有专门的 `<dcmotor>` 执行器**，参数可直接对着电机数据手册填：
`resistance`（R）、`motorconst`（Kt/Ke）、`nominal="voltage stall_torque no_load_speed"`、`inductance`、
`saturation="torque current current_rate"`、**`thermal="resistance capacitance timeconst tempcoef reftemp ambient"`（热模型）**、
`controller="kp ki kd slewmax Imax Vmax"`（**内置电流环**），甚至还有 `cogging`。
另有一个**独立的 `pid` 执行器**。关节级还有 `frictionloss`（库仑摩擦）、`damping`（粘滞摩擦）、
**`lugre="stiffness damping coulomb static stribeck"`（Stribeck/LuGre 摩擦模型）**，
以及 `gear`（**3.7.0 起 `damping`/`armature` 会按 gear² 正确反射**）。
来源：[MuJoCo XML 参考 actuator/dcmotor](https://mujoco.readthedocs.io/en/stable/XMLreference.html#actuator-dcmotor)

**所以真正的缺口不是"造不出来"，而是"我们完全没接"**：

| 项 | MuJoCo 有没有 | 我们有没有用 |
|---|---|---|
| 直流电机（R/Kt/Ke/电感/热/饱和/cogging） | ✅ `dcmotor` | ❌ |
| 电流环 / PID 执行器 | ✅ `controller=` / `pid` | ❌ |
| 库仑 + 粘滞摩擦 | ✅ `frictionloss` / `damping` | ❌（模型里没设） |
| **Stribeck / LuGre 摩擦** | ✅ `lugre` | ❌ |
| 减速比 | ✅ `gear`（+gear² 反射） | ❌ |
| **回差 backlash** | ❌ **官方没有参数**（建议用位置相关阻抗 `solimp` 近似） | — |
| 齿轮箱柔性 | △ 可用 `stiffness`/`damping` 近似 | ❌ |
| 真三级级联（电流/速度/位置） | ❌ 无人内置（Gazebo/Isaac/CoppeliaSim 也没有） | — |

**影响**（这才是要紧的部分）：
- **参数辨识的结论对不上真机**：真机的"力矩→运动"关系里有减速器与摩擦，我们辨识出的质量/惯量只在"理想扭矩源"假设下成立；
- 做不了"电机选型 / 电流限制 / 发热"这类工程问题；
- 抓取/接触任务的力控精度不可信。
**补的成本**：**低~中（比我原先估的低）**。"电机 + 传动 + 摩擦"大部分是**现成积木，改模型 XML + 加界面参数**即可；
量级 **2~5 天**（把 `工具/导入模型.py` 生成的 `_torque.xml` 扩成"可选 `_dcmotor.xml` 变体 + 界面填电机铭牌参数"）。
**真正需要自研的只有"回差"**（全体软件都没有，属增值项）。

> **顺带一个对做项目的提示**：这条正好说明"**先查官方有什么，再决定自研什么**"。
> 我们（和原规划）都以为要做电机模型，实际官方早就做好了，只是没被暴露到 Python 层。
### 3.3 批量并行 / 强化学习：完全没有（影响：**中~大**，取决于您要不要做 RL）

**现状**：单环境单线程（`启动.py`：主线程窗口 + 1 个后台仿真线程，注释就写明"物理+控制律放同一工作线程，别拆"）；无 `mjx`/`jax`/多环境/Gym 接口（grep 全空）。
**业界（调研实测事实，附来源）**：
- **MJX-JAX 官方把 Apple Silicon 列在支持范围里**（[MuJoCo MJX 文档](https://mujoco.readthedocs.io/en/stable/mjx.html)原文："runs on Nvidia and AMD GPUs, Apple Silicon, and Google Cloud TPUs"）；
  **但"能用"和"能用 GPU"是两件事**：JAX 官方[支持平台表](https://docs.jax.dev/en/latest/installation.html)里，
  macOS aarch64 的 **CPU = yes**、**Apple GPU = "experimental"**（原文专门一节：*"JAX is not supported on Mac/OSX GPU; instead use the standard CPU installation commands"*）。
  → **结论：在本机跑 MJX 是可行的，但要按"CPU 批量"预期，别指望 Apple GPU 加速**（这是本次调研里我自己更正过的一条）。
- **官方也写明：单场景仿真 MJX-JAX 可能比 C MuJoCo 慢 10×** —— 它的强项是"成千上万环境并行"，不是"单场景更快"。
- **MJX-Warp**（性能最好的那条路，Humanoid 场景实测 **3.35M 步/秒**）**只针对 NVIDIA GPU**；Mac 上只能走 CPU。
- **Isaac Sim / Isaac Lab：官方要求 Ubuntu 22.04+/Windows 11 + NVIDIA GPU**（`--num_envs` 多环境），**macOS 完全不支持**；**Habitat 官方 issue 标题即 "Only Linux 64 support"**。
- **调研拿到的官方吞吐基准**（[MJX 文档](https://mujoco.readthedocs.io/en/stable/mjx.html)，单人形模型）：**Apple M3 Max 的 CPU MuJoCo = 65 万步/秒**、64 核 AMD = 180 万、A100（batch 8192）= 95 万、8 芯 TPU v5（batch 16384）= 270 万；**MJX-Warp 纯 Warp = 335 万步/秒**。
  ★ 注意第一项：**Mac 的 CPU 版本本身就能跑到 65 万步/秒**，这比我们界面里的实时节拍快了几个数量级 —— 说明"批量跑"在 Mac 上并不是没戏。
- **Genesis World 是唯一在官方矩阵里明确把 Apple Silicon GPU 列为 ✅ 的**（后端 CUDA→ROCm→**Apple Metal**→CPU；代价：**Metal 不支持 double 精度**，GPU 确定性只部分支持）。
- **ManiSkill / SAPIEN 在 Mac 只能 CPU 仿真**；且 **ManiSkill 的资产是 CC BY-NC 4.0（非商用）** —— 对我们这种要闭源落地的软件是红线。
**影响**：不能在本软件里训 RL；不能一次跑 100 组参数做批量实验。
**补的成本**：**中（比原先估计的低）**。因为 **MJX-JAX 官方支持 Apple Silicon**，"在本机做 GPU 批量"这条路是通的；缺的只是"把批量跑和分析接到软件里"。
**建议**：**不要**把 RL 训练塞进带界面的主程序（官方也承认"更多环境不等于更快训练"）；做成**独立的批处理进程**（无窗口、MJX 批量、参数网格 + CSV 汇总），本软件当"可视化调试器 + 结果查看器"。这样既拿到吞吐，又不破坏现在这个"双击就开"的体验。

### 3.4 CAD / URDF 导入：没有（影响：**中**）

**现状**：模型库加载器只接 `.xml / .mjb / .mjz`（`模型桥.py` 的文件选择器提示语即此）；`模型/` 下 **0 个 URDF**；导入工具（`工具/导入模型.py`）是"从 menagerie 挑现成 XML"。
**业界（调研事实）**：URDF 是 ROS 世界的通用格式（Gazebo/CoppeliaSim/Isaac/MuJoCo 都支持导入）。
**但 CAD（STEP/IGES）直接导入 —— 11 款受查软件里全部"未查证"**：
MuJoCo 官方直接建议"先用 MeshLab 之类的工具转成 OBJ/STL"，CoppeliaSim 强在网格编辑（凸分解/HACD/V-HACD）但也不是 STEP/IGES 原生导入。
**即：这条我们缺，但并没有一个"别人都有、就我们没有"的现成对手** —— 如果我们真做出来，反而是差异点。
**影响**：您想仿真的**自家机械臂**（只有 URDF 或 CAD）现在进不来，只能先手工转成 MJCF。
**补的成本**：**低**。`mujoco.MjSpec.from_file`（实测 `hasattr == True`）**原生支持 URDF**（官方 modeling 与 changelog 均有记载，
还支持在 `<robot>` 里内嵌 `<mujoco>` 做补充），缺的是"界面上让它进来 + 自动生成 `_torque`/`_actuator` 变体"这一步。量级 **1~3 天**。
**但 CAD（STEP/IGES）是重工程**：MuJoCo **没有 CAD 内核**，网格格式**硬限制在 `stl / msh / obj`**
（`msh` 只给 flex 体用），所以"STEP → 带装配层级的 MJCF（凸分解 + 惯量 + 材质 + 关节轴推断）"需要自建转换链，
量级 **数周**；调研确认**只有 Isaac Sim（NVIDIA，Mac 上跑不了）有真 CAD 导入**，其余全部未查证。

### 3.5 运动规划 / 任务级能力：只有演示级（影响：**中**）

**现状**：没有规划器；`末端两点运动` 插件是"雅可比转置 + 逆运动学 + smootherstep"，是演示，绕障/多解/奇异点处理都没有。
**业界**：MoveIt（ROS2）是事实标准；Isaac/CoppeliaSim 都有任务级规划与抓取管线。
**影响**：抓取、避障、装配这类任务现在只能自己写，容易撞奇异点。

> **附：与我们"参数辨识"相关的一条精化（第三路调研勘误）**
> 官方 `mujoco.sysid` **没有专门的可辨识性/灵敏度分析**，只有一个**数值条件数诊断**：
> `optimize(check_conditioning=True)` → `_warn_if_ill_conditioned`，当 `cond(JᵀJ) > 1e12` 时告警
> *"the problem may be ill-conditioned. Consider x_scale='jac' or regularizing."*
> （源码已核验：`python/mujoco/sysid/_src/optimize.py`）。
> **我们的辨识器**（自研 Gauss-Newton）同样只做了"收不收敛/拟合改善多少倍"的判断。
> → **"结构可辨识性分析"（哪些参数在这段轨迹上根本不可辨识）是全体空白**，
> 而我们踩到过真实例子（质心位置在这类轨迹上不可辨识，所以默认只辨识 3 个连杆质量）。
> **这是一条可写进"我们的差异化"的具体项**：把"不可辨识参数自动提示/剔除"做成功能。
**补的成本**：**中~高**（接 MoveIt 需要一个 ROS2 环境，与"纯 Python 单进程"的现状冲突）。**建议**：先在软件里加"关节空间轨迹插值 + 奇异点提示"，任务级留给 ROS 侧。

### 3.6 界面中文：结构性做不到（影响：**小~中**）

**现状**：界面全英文（`界面文字.py` 把中文术语翻成英文再画）；根因是**Python 绑定没有字体加载入口**（`AddFontFromFileTTF` / `ImFontAtlas` 都没有，`FontGlobalScale` 只读），官方字体又没有 CJK 字形。
**业界（调研事实）**：**11 款受查软件里只有 Webots 官方内置中文界面**（官方文档列了法/德/西/中/日翻译）；
Genesis 只有中文**文档站**（不是 UI 本地化）；其余全部"未查证/无 i18n"。
**补的成本**：**高**（要改官方 C++ 重编译，5~15 天，且违背"不改官方源码"这条我们已经守住的红线）。
**建议**：**维持现状**（中文进终端与文档），这条**不值得**为它破红线 —— 而且"没有中文界面"是**全行业的常态**，不构成我们的竞争劣势。

### 3.7 平台/分发：只有 macOS 原生（影响：**小**，除非要给别人用）

**现状**：`.app` 是 macOS 原生 arm64（`工具/打包应用.py` 生成），启动脚本用 bash；无 Windows/Linux 包、无 Web/远程访问（原规划已排除 `launch_web`，wheel 缺 WASM 客户端）。
**影响**：换 Windows 机器的同事用不了。
**补的成本**：**中**（需要另一套环境+打包，且 macOS 的线程排法在别的平台要重验）。

### 3.8 其他小缺口（一句话各一条）

| 缺口 | 现状 | 影响 |
|---|---|---|
| **多视口** | 只有 1 个 3D 视口 | 对比"改前/改后"要开两个进程 |

### 4.4 关于 MuJoCo Studio 的官方定位（与我们直接相关）

调研拿到了官方**唯一公开表述**（MuJoCo 文档 Visualization 章节的 note 框原文）：

> **MuJoCo Studio** — *We are actively developing a new visualizer platform called MuJoCo Studio.
> We will update this section once it becomes more established.*
> —— [MuJoCo 文档源码](https://mujoco.readthedocs.io/en/stable/_sources/programming/visualization.rst.txt)

- **没有正式文档页**（readthedocs 全站导航无 Studio 章节）；**Python 官方文档列的模块里既没有 `mujoco.experimental.studio`，也没有 `mujoco.sysid`**。
- 官方**没有逐字写"API 不稳定"**，用的是"actively developing / once it becomes more established" → **准确表述是"官方未承诺 API 或行为稳定性"**。
- 从官方源文件 `src/experimental/studio/app.h` 可确认它**实际具备**：Filament 渲染 + Dear ImGui/ImPlot + **Spec Explorer/Spec Editor（图形化在线改模型结构）** + `SimHistory` 时间线回放 + Profiler + PiP 多视口 + `StepControl`。
- **对我们的意义（两条）**：
  1. **风险**：我们整个软件建立在官方"未承诺稳定性"的实验层上 —— 所以 `骨架/官方接口清单.py` 的 24 项自检 + `零改动自检.py` 的哈希钉住**不是过度设计，是必需品**；
  2. **机会**：官方下一步要补的正是"图形化 spec 编辑 + 更多面板 + 时间线回放 + profiler"—— 这几项我们现在就有（工作台页签、录制回放、监控曲线、皮肤），**在"官方还没做完"的窗口期，我们处于相对领先**。

## 五、优化建议（按"性价比"排序）

> 口径：**改动量 / 收益 / 风险**。P0 = 立刻做，P1 = 值得做，P2 = 看需求，P3 = 不建议做。

| 优先级 | 建议 | 改动量 | 收益 | 风险 |
|---|---|---|---|---|
| **P0** | **接上 MuJoCo 传感器读数（先做 接触力/关节力矩 + 位置速度 → 监控面板画曲线）** | 2~4 天 | 接触力与关节力矩**可量化**，抓取/力控调试不再靠猜；**当前收益最高、风险最低**的一项 | 低 |
| **P1** | **把仿真循环里那句 `sleep(0.0002)` 换成「混合等」（sleep 到接近 deadline 再忙等）** | 1 天 + 复测 | 迭代次数实测提高一个量级（14 秒内 3.7 万 → 26 万步）；时间比 0.86× 有望贴近 1.00×；且不再每圈白睡 0.2 ms | 低（**必须先复测「时间比」是否真的改善**，见 6.2） |
| **P1** | **支持 URDF 导入**（`MjSpec.from_file` 已实测可用）+ 自动生成扭矩/执行器变体 | 1~3 天 | 自家机械臂能进来，不再依赖 menagerie | 低 |

## 六、性能实测（本次评估新增，含一次"我自己的误判"更正）

### 6.1 引擎与控制回路的真实能力（都是实测）

| 项目 | 实测 | 换算 |
|---|---|---|
| **`mj_step` 单线程**（UR5e 扭矩模型，dt=2 ms） | **2.87 µs/步** | **34.9 万步/秒 = 698× 实时** |
| 完整 Python 控制回路（numpy 控制律 + `mj_step`，Phase 0 同机实测） | 8.13 µs/步（p99 8.96） | 理论上限 **123 kHz** |
| 定频 1000 Hz 闭环 | 占空比 **7.07%**，**0/2000 超期** | 控制频率钉 1 kHz 安全 |
| macOS 延时精度 | `sleep` 过冲（100 Hz 实测只有 83.8 Hz） | **必须 hybrid（sleep + 忙等）** |

> **结论**：**引擎完全不是瓶颈**（698× 实时）。瓶颈在"官方怎么节拍"这一层。

### 6.2 界面里到底跑多快（A/B 实测，同一台机器、同一模型）

**方法**：固定墙钟 14.0 秒，唯一变量是 `启动.py` 里的 `_time.sleep(0.0002)`。

| 版本 | 墙钟 | 仿真时间 | 步数 | **时间比（仿真/墙钟）** | 迭代次数 |
|---|---|---|---|---|---|
| **现状（带 `sleep(0.0002)`）** | 14.0 s | 12.0 s | 37,100 | **0.86×** | 3.7 万 |
| **去掉该 sleep** | 14.0 s | 12.0 s | 261,504 | **0.86×** | **26.2 万** |

**两点必须讲清楚（这也是我一开始判断错的地方）**：

1. **时间比完全一样（0.86×）** —— 因为官方 `StepControl.set_speed()` 的**上限被钳在 100%**（实测其文档原文：*"Sets the desired speed (clamped to [0.1%, 100%])"*），**节拍是墙钟驱动的**。所以**删掉那句 sleep 并不会让仿真变快**，它只是让同一段仿真时间用更多（更细的）迭代去完成。
2. **但这句 sleep 确实浪费**：每圈固定睡 0.2 ms。在 14 秒里它把迭代次数从 26.2 万压到 3.7 万 —— 也就是说**"响应界面事件"和"事件处理精度"被它拉低了 7 倍**（每圈 0.2 ms 的粒度）。正确做法不是删掉（那是空转烧 CPU），而是换成原规划里就论证过的 **hybrid 等**（睡到接近 deadline 再忙等）。

**为什么它没被早发现**：这句注释写的是"避免极端情况下空转"，看起来是保守的良性代码；而 `0.86×` 这个数字**不会让任何人觉得有问题** —— 直到把它拿去 A/B 才看出迭代粒度差了一个量级。

### 6.3 一个仍然开放的疑点（建议做成可行性探针）

实测时间比是 **0.86×**，而引擎能力是 **698×**。0.86 是"官方节拍器 + 界面线程争 CPU"共同作用的结果，但**为什么连 1.00× 都没到**，目前只有推断没有证据：
- 推断 A：官方 `StepControl.advance()` 按"刷新预算"决定这一步推多少，预算里含渲染时间；
- 推断 B：Mac 上 Python 主线程（窗口）+ 仿真线程竞争 GIL/CPU；
- 推断 C：那句 sleep 让"本次预算没花完"。

**建议**：先做一个**只测时、不改功能**的探针（不动官方代码，只记录每圈 `advance()` 的耗时与步数），把这条查清。**在查清之前，不要把"加速"写进任何优化清单** —— 这也是我在第五节把它降级到 P2（先探针）的原因。

| 不建议 | 理由（取证） |

| **为了中文界面去改官方 C++ 重编译** | 违背我们**唯一守住的红线**（不改官方源码，靠 `骨架/官方接口清单.py` 24 项自检 + `零改动自检.py` 哈希钉住）。而且中文只影响观感，不影响任何一个功能 |
